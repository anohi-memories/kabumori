# HTTP / AI / Web Search 概算コストモデル（N1）

- 作成: 2026-09-28（N1 調査。設計のみ）
- 方針: **料金が公式に確認できないものは推測せず「要確認」**。件数は 2026-09-28 の少数サンプル実測（1 feed 1回取得）からの推計で、**平日・重大イベント日には増える**。実装後は usage metering の実測で置き換える。

## 0. 結論

| 項目 | 無料feed主体（本案） | 備考 |
|---|---|---|
| HTTP 取得 | 約 270回/時、約 6,500回/日 | 条件付き GET で大半は 304 / 小容量 |
| 取得記事（重複除去前） | 約 2,000〜3,500件/日 | PR TIMES が最大（平日は要実測）。JMA 定常電文は別枠 |
| ルール filter 後のクラスタ | 約 200〜500/日 | |
| AI 一次判定（batch） | 約 60〜150回/日（1回 20〜40見出し） | 軽量モデル。費用は1日 $0.1〜0.3 程度の見込み（単価は既存監査の前提値） |
| Web Search | **約 5〜40回/日**（上限をコードで持つ） | 発見ではなく補完専用 |
| Web Search 月間 | 約 150〜1,200回/月 | 1回 約 $0.013（幅 $0.011〜0.02、既存監査の推定値）→ 約 $2〜24/月 |

- 参考：2026-09-19 監査時点の Web Search 主体方式は、20分巡回で**約 280回/日（約 8,400回/月、約 $110/月 相当）**。その後 cost-optimization 側で頻度・方式の変更が進んでいるため、**現在値は usage metering の実測で確認すること**（本書では断定しない）。
- **重要な前提**: 国内大手報道・PR TIMES 等は規約上そのまま使えない（catalog §3）。許諾・契約なしで運用する場合、報道起点の分野（戦争・事故・国内一般）は Web Search 補完に残るため、**Web Search は上限側（40回/日前後）に寄る**と見込む。
- 監査時点を基準にすると Web Search 回数は **約 85〜98% 減** の見込み。ただしこれは「新基盤で Recall が確保できた場合」の話で、**Recall はベンチマーク（news_recall_benchmark.md）で実証するまで前提にしない**。

## 1. 前提とする source 構成（N2 の初期案）

| 区分 | 本数 | 巡回間隔（市場時間 / 時間外） | 1時間あたり取得（平均） |
|---|---:|---|---:|
| 速報性の高い報道・通信（GDELT ＋ 許諾・契約済みのもののみ。**国内大手 RSS は規約上不可**） | 10 | 10分 / 20分 | 約 45 |
| 公式・発表時刻既知（FRB/日銀/ECB/BoE/BLS/BEA…） | 15 | 30分（発表前後は1〜2分） | 約 30＋発表時バースト |
| 公式・不定期（USTR/White House/State/Federal Register/SEC/金融庁/防衛省…） | 15 | 15分 / 30分 | 約 50 |
| 災害（JMA 高頻度 / USGS / GDACS / NHC） | 4 | 1〜2分（JMA）、5分（他） | 約 70 |
| 業界・プレスリリース | 20 | 30分 / 60分 | 約 35 |
| 企業 newsroom | 10 | 60分 / 120分 | 約 8 |
| **合計** | **74** | | **約 240〜280（≒ 6,000〜6,700/日）** |

- 発表時バースト: 主要指標・会合は1日0〜3件。1件あたり前後20分を1分間隔 → 最大 +60回/日。
- **Edge Function の起動回数**は HTTP 回数ではなく巡回サイクル数（例: 1分ごと → 1,440回/日、約 4.3万回/月）。Supabase の料金（プラン内の起動回数枠・超過単価・egress の扱い）は**要確認**（公式料金ページで確認してから確定する）。
- 帯域: feed 1件あたり数KB〜数百KB。JMA 高頻度 feed は大きいため差分取得が前提。月あたり数GB〜20GB程度と見込むが、**Supabase 側の課金対象かは要確認**。

## 3. AI 判定の推計

| 段階 | 件数/日 | 手段 | 費用見込み |
|---|---:|---|---|
| 重複除去 | 2,000〜3,500 → 1,500〜2,800 | コード | 0 |
| feed 除外・ルール filter | → 400〜900 | コード | 0 |
| クラスタ化 | → 200〜500 クラスタ | コード | 0 |
| 一次判定（batch 20〜40件/回） | 60〜150回 | 軽量AI（Luna 相当） | 1回 約3k入力/1k出力として 約 $0.002/回 → **$0.1〜0.3/日**（単価は既存監査の Luna $0.2/$1.2 per 1M の前提。現行単価は要確認） |
| 企業 alias 曖昧解消（batch） | 5〜20回 | 同上 | 数セント/日 |
| 深い判定 | 一次判定で残った件数 | **既存 judgement（Luna→Sol）。変更しない** | 既存の費用構造のまま（件数が増えれば比例） |

- 注意: 新基盤で候補が増えると、**既存 judgement（特に Sol 昇格）の件数が増えてコストが上がり得る**。既存監査では判定費用の約9割が Sol 昇格。新基盤から既存判定へ渡す件数の上限（例: 1日 N 件）を接続時に決める必要がある（接続は N1 範囲外）。

## 4. Web Search の推計

| 発火条件 | 1日あたり見込み | 根拠 |
|---|---:|---|
| 市場異常なのに原因クラスタなし | 0〜5 | 異常自体が平常日 0〜数件（要実測）、多くは記事プールで説明可能 |
| source 間の食い違い | 0〜5 | 重大事象の日のみ |
| 一次情報が見つからない重要候補 | 2〜15 | 報道のみの地政学・事故 |
| 時刻不明・詳細不足 | 1〜10 | Nikkei Asia / @Press など時刻なし feed |
| internal_trigger_only source でのみ発見 | 2〜10 | 表示可能な出典探し |
| **合計（上限 40/日をコードで設定）** | **5〜40** | |

月間: 150〜1,200回。1回 約 $0.013（幅 $0.011〜0.02。docs/news-cost-optimization/AUDIT_AND_PLAN.md の推定値）→ **約 $2〜24/月**。

## 5. 方式比較（概算）

| 指標 | Web Search 主体（2026-09-19 監査時点、20分巡回） | 無料feed主体（本案） |
|---|---|---|
| 発見方法 | トピック検索（固定3＋回転1/巡回） | 74 source 定点巡回＋ルール＋batch AI |
| HTTP | 少（検索 API 呼び出しのみ） | 約 6,500/日（無料） |
| Web Search/日 | 約 280（429 障害なしの換算） | 5〜40 |
| Web Search/月 | 約 8,400 | 150〜1,200 |
| Web Search 費用/月 | 約 $110（推定） | 約 $2〜24 |
| 一次判定 AI | 検索1回ごとにモデル出力 | batch で $3〜9/月 |
| 有効候補率 | 48h で 5件/366検索（空振り 99%） | 要実測（benchmark） |
| 追加の固定費 | なし | なし（無料 source のみの場合） |

- **現行（2026-09-28）の Web Search 回数は、cost-optimization 側の変更（毎時化・headline trigger 等）で監査時点から変わっている**。比較の正本は usage metering の実測にすること。

## 7. 不確定要素

1. PR TIMES の平日件数（最大の件数要因）。
2. 報道 RSS の商用・AI 処理の許諾（許諾が取れない source は `internal_trigger_only` か不使用になり、Web Search 補完が増える）。
3. 市場異常トリガーの有無（無料日次のみなら日中の補完は Web Search 側に残る）。
4. 既存 judgement に渡す件数の上限（Sol 費用に直結）。
5. Supabase の起動回数・帯域の課金条件（要確認）。
