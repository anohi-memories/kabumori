## 1. 1 回の試みの順番と、SQL のロック（読み取りで確かめた）

| # | 呼び出し口（プロセス A） | SQL のロック・確認 |
| --- | --- | --- |
| 1 | `ai_calls_claim`（最初） | 利用者の共有の advisory lock → 呼び出しの番号の advisory lock → 行の `FOR UPDATE`。無ければ acquired の行を作る |
| 2 | `ai_ledger_reserve`（試み n） | 台帳全体の advisory lock。同じ（番号、試み n）が既にあれば、reserved のときだけ再利用。sent・確定・released は拒む（`ATTEMPT_IN_FLIGHT` / `ATTEMPT_FINALIZED`） |
| 3 | G5 の再確認 | （SQL なし） |
| 4 | **`ai_calls_claim`（確認。PR #357）** | 1 と同じロック。行が acquired なら `busy`（書き込みなし）、閉じていれば `complete`、別の ID なら `conflict`、行が無ければ**新しい行を作る** |
| 5 | `ai_ledger_mark_sent` | 予約の行の `FOR UPDATE`。reserved で期限内のときだけ sent にする。それ以外は `may_send: false` |
| 6 | AI へ送る → `settle` → … → `ai_calls_complete` | complete は持ち主（claim のトークン）と acquired を求める（違えば FENCED） |

復旧（プロセス B）の側:

- `ai_ledger_recover_stale`: 期限切れの reserved を released に、猶予を過ぎた sent を上限額の unknown にする（`SKIP LOCKED`）。
- `ai_calls_abandon`: 呼び出しの番号の advisory lock → 行の `FOR UPDATE` → **同じトランザクションの中で台帳を読み**、reserved / sent が 1 つでもあれば `LEDGER_NOT_FINAL` で閉じない。

### 隙間が無いこと

予約（2）は、確認（4）より前に commit されている。閉じる操作（abandon、X）と確認（4、F）の順番は、次の 2 通りしかない。

- **X が先**: F は同じ advisory lock を待ち、X の commit の後に読む → 閉じた行を見て送らない。試験 L-a で、F が X の commit まで約 2 秒待ったことを測った。
- **F が先**: X の台帳の読み取りは F より後、つまり 2 の commit より後 → reserved を見て `LEDGER_NOT_FINAL`。試験 L-b で、abandon の答えが `{abandoned: false, reason: LEDGER_NOT_FINAL, open_attempts: 1}` だった。

その後（4 → 5）の間も閉じられない（予約が開いている）。期限切れで recover_stale が予約を戻した場合は、5 が `may_send: false` を返す。

確認を予約の**前**に置くと、確認と予約の間に閉じられて送ってしまう。わざと壊した写し `check_before_reserve` を、7 件の試験が見つけた。試験「確認の直後で止める」では、正しい順番なら復旧は `WAIT_LEDGER_OPEN` で待ち、呼び出しは OK で終わる。

## 2. 「busy」は持ち主の証明ではない — それでも 2 回は送らない理由

`ai_calls_claim` は、acquired の行に対して `busy` しか返さず、持ち主を教えない。次の流れでは、止まっていたプロセスの確認が、**別のプロセスの行**に対して `busy` を受け取る。

1. 止まっている間に、復旧が行を閉じる。
2. `ai_calls_forget_user` が行を消す。
3. 再起動が同じ番号で新しい行を取る。

そのときに送りを止めるのは、台帳の（呼び出しの番号、試みの番号）の一意の決まりと、その状態の機械（4 層）。

1. reserve が、確定・released・sent の試みを拒む。
2. mark_sent が、reserved 以外を拒む。
3. 状態の変化のトリガーが、released → sent を拒む。
4. 表の制約 `reservations_state` も、released → sent を拒む。

確かめたこと:

- **止まっていたのが予約の後**: 確認は `busy` で通る（`mark_sent` まで進んだことを記録で確認）。しかし、自分の予約は戻されているので `may_send: false`。再起動も試み 1 が released なので拒まれる。**送信 0**。
- 壊した写し: 層 2 だけ、層 2 と 3 を壊しても送信は 0 のまま（層 4 が止める）。実質同じ動きとして記録した。

### 残るもの R1（共有の SQL が要る）

止まっていたのが**予約の前**（claim の直後）だと、次のように進む。

1. 復旧が閉じ、`forget_user` が行を消し、再起動が新しい行を取る。
2. 止まっていたプロセスが再開する。予約（試み 1 は未使用なので通る）→ 再確認 → 確認（`busy`、再起動の行）→ **送る**。
3. 再起動のほうは、予約で試み 1 が確定済みのため止まる。

試験で、次のとおり実際に起きた。

- 送信 1、台帳に実額 1 件。**二重の送信・二重の課金は無い**。
- しかし、生きている行（再起動のもの）は「送っていない」（`POLICY_DENIED`、`attempts: 0`、`no_request`）と記録する。その人への最初の答えは `LEDGER_UNAVAILABLE`、頼み直すと `NOT_SENT`。答えと記録が事実と違う。

起きる条件:

- 人の行: `forget_user` を「その人がもう認められない」前に動かした場合だけ。SQL の説明にある前提を破った場合で、守れば、止まっていたプロセスは確認より前の G5 の再確認で止まる（試験で確認）。
- system の行: `ai_calls_forget_system_brand` で消した後に、運営の仕事が同じ操作 ID でやり直す場合（G5 の再確認が無い）。

直し方の案（どれも未実装）:

- (a) 共有の SQL（推奨）: 確認で持ち主を証明する。例: `ai_calls_claim` に `owner` を渡したときは「その持ち主の acquired の行」のときだけ `held` を返し、行が無いときに作らない。明示の承認と Codex Sol（高）が要る。
- (b) G6 だけで: 予約が `ATTEMPT_IN_FLIGHT` / `ATTEMPT_FINALIZED` で拒まれたとき、「送っていない」ではなく UNKNOWN と記録・回答する。ほかの誰かが同じ番号で送った可能性があるため。答えは正直になるが、止まっていたプロセスの送信自体は止められない。今の guard はこの理由を細かく渡さないので、試験と設計の確認が要る。今回は入れていない。

## 3. 確認が失敗するとき（fail closed の代わりに失うもの）

## 4. 権限の窓（残るもの R2）

順番は「再確認 → 確認 → mark_sent」。**再確認の後**に持ち主の世代が変わっても気づかない（試験で、確認の直後に世代を変えると送られた）。

窓は RPC 2 回分（確認・mark_sent）。順番を「確認 → 再確認 → mark_sent」にすると、窓は mark_sent の 1 回分に縮む。§1 のとおり、確認は予約の後ならどこでも安全なので、入れ替えても閉じる操作との隙間は生まれない。レビューで決めてほしい（今回は変えていない）。

どちらの順番でも、送信中の呼び出しは止められない。G6 の決まり（「最後の確認の後は止められない」）のとおり。
