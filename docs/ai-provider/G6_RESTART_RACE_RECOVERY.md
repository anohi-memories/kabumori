## 0. まとめ

呼び出し口（プロセス A）と復旧（プロセス B）を、**別々の OS プロセス**として動かす試験の仕組みを作った。プロセスが止まる場面は、そのプロセスを SIGKILL して作る。
結果はすべてデータベースで確かめる。対象は `ai_calls` の行、台帳の予約と使用の記録、偽の AI が受け取った要求の記録（答える前に書くので、強制終了の後にも残る）。

**見つけた不具合 1 件（G6 の持ち物）を直した**。

- 症状: プロセスが claim の直後で長く止まると、その間に復旧が「送っていない（NOT_SENT_PROVEN）」として行を閉じる。その後でプロセスが再開すると、**閉じた後に AI へ 1 回送っていた**。
- 直し: `gateway.ts` で、送る直前（予約の後、送信の確定の前）に「claim がまだ自分のものか」を確かめる。閉じられていれば送らない。

直した後は、試した場面のどれでも次が成り立つ。

- 送り直しは 0。
- 台帳が費用の正本のまま。
- 人・ブランド・アプリをまたがない。
- 古いセッションや、変わった持ち主の世代では通らない。

## 2. 見つけた不具合と直し

### 再現（直す前）

1. プロセス A が claim の直後で止まる。
2. 時間が過ぎる（SQL の決まりの 300 秒と、決まりの最長の実行時間の両方を超える）。
3. 復旧 B が行を「送っていない」として閉じる。墓石の控えは `attempts: 0`・`no_request`・0 USD。
4. A が再開する。予約、送信の確定、**AI への送信 1 回**、実額での精算と進む。
5. 記録は FENCED で拒まれ、A は UNKNOWN を返す。

その結果、次の 2 つが起きた。

- 墓石は「送っていない」と言うが、AI は要求を受け取った。
- 台帳には実額の使用（0.000232 USD、measured）が 1 件ある。`ai_calls` の控えは台帳と合わない。

台帳は正しく数えていたので、費用の数え漏れは無い。しかし「閉じた操作の後で送らない」が破れていた。

### 直し（`supabase/ai_gateway/gateway.ts`）

試みごとに、次の順番で進む。

1. 台帳の予約
2. 権限の再確認
3. **claim がまだ自分のものか**（既にある `ai_calls_claim` を同じ ID で呼ぶ）
4. 送信の確定
5. 送信

- 答えが「処理中（busy）」なら、まだ自分のもの。続ける。
- 閉じている・別の中身・読めないときは送らない。予約は戻し、UNKNOWN を返す。行には何も書かない（墓石を上書きしない）。

### 隙間が無い理由

- 復旧の `ai_calls_abandon` は、台帳に開いた試みが無いときだけ閉じる。行のロックを持ったまま、同じトランザクションで台帳を読む。
- この試みの予約は、確認より前に台帳に入っている（開いている）。
- 確認の claim も同じ行のロックを取る。
- そのため、閉じるのが先なら確認で気づく。確認が先なら、閉じる側は開いた予約を見て拒む（`LEDGER_NOT_FINAL`）。
- 確認の後で送っている間は、台帳が開いている（sent）。復旧は送信済みの猶予（900 秒）を過ぎるまで閉じない。過ぎた後の遅い答えは次のように扱われ、A は UNKNOWN を返す。
  - 精算は SQL が拒む（SETTLEMENT_CONFLICT）。
  - 記録も拒まれる（FENCED）。
  - 費用は上限額のまま。

費用: 試みごとに RPC が 1 回増える（既存のテストの呼ぶ順番を 4 か所直した）。

例外: 利用者の削除で行が消えた後だと、確認の claim が新しい行を作る（acquired）。この場合も送らないが、その行は残る。復旧が NOT_SENT_PROVEN として閉じる。

## 3. 確かめたこと（隔離 PG17、7 PASS、うち 1 は準備）

| テスト | 確かめたこと |
| --- | --- |
| 止まる場所 6 か所 | 生きているプロセスの行には、2 つの復旧を同時に動かしても触れない（DB は 1 バイトも変わらない）。強制終了の後の再起動は IN_PROGRESS（記録済みのものは OK）で、送信 0。時間が過ぎた後、2 つの復旧と 5 つの再起動を同時に動かしても、再起動は IN_PROGRESS か UNKNOWN で、送信 0。各行は 1 回だけ閉じる。分類は NOT_SENT_PROVEN×2 / POSSIBLY_SENT×2 / RESULT_LOST。期限切れの予約を戻すのは 1 回、上限額の不明にするのは 2 回。控えは台帳と一致し、使用の記録は確定した試みごとに 1 件。その後の再起動は UNKNOWN（記録済みは OK）で、送信 0 |

## 4. 解けないもの・確かめられないもの

1. **NOT_SENT_PROVEN でも「不明」でしか閉じられない**（G6-06 から変わらず。`BLOCKED_SQL_NO_NOT_SENT_CLOSE`）。この試験では、claim の後・予約の後の行は AI への送信 0 なのに、答えは UNKNOWN になる。
2. **呼んだときの決まりの版が残らない**。復旧は、自分の動いている版を控えに書く。送り直しは起きない（版が違えば別の中身、同じ版でも墓石は UNKNOWN）。ただし控えの版は正確ではない（BLOCKED。SQL に版の欄が要る）。
3. **記録できた行の控えと台帳のずれ**は、今の RPC では読めない（G6-06 から変わらず）。
4. 送信済みの猶予（900 秒）は、1 回の試みの最大時間（600 秒）より長いことが前提。運用で短くしないこと。
5. 確かめられないもの（NOT_VERIFIED）:
   - 本物の G5 の RPC（未実装）。偽物の答えは PR #340 / #345 の形に合わせている。
   - Edge に置いたときの動き（PR #350 の変更案は未適用）。
   - AI のプラン。
   - 本物の OpenAI / Anthropic。
   - 本物の Supabase（PostgREST・接続の数・時間切れ）。
   - スケジューラ。
