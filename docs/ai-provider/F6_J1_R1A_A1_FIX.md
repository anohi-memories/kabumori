## 1. R1a: コメントを挟んだ読み込みが検査をすり抜けた（`isolation_test.ts`）

### 何が問題だったか

- ECMAScript では、`import` と `(` のあいだにコメントや改行を書ける。#219 の検査は `import` と `(` のあいだに空白しか認めていなかった
- J1 の再現: 許可された bridge に `import/* audit */("../ai_provider/mod.ts")` を足すと、`mod.ts` の公開名がすべて使えるのに、F6 の検査 12 件と H5 の検査 2 件（計 14 件）がすべて通った
- 同じ穴が他にもあった
  - `from/* c */"..."`（`from` のあとのコメント）と、`import/* c */"..."`（中身を読まないだけの読み込み）
  - 読み込み先の文字列の中の行の継続（`\` のあとの改行）。#219 は文字列の中の改行を認めず、読み込みそのものを見落とした
  - エスケープ（`\x5f` など）を含む読み込み先は、解読せずに見ていた

### どう直したか（許可リストは広げていない）

- **トークンのあいだの「trivia」を ECMAScript どおりに認める**
  - 空白と改行（Unicode の空白、U+2028 / U+2029、BOM を含む）、`/* */` のコメント、`//` のコメント
  - `import`・`from` と、次のトークン（`(`、文字列）のあいだで認める。`import()` の引数の前後でも認める
  - 読み込みを表す書き方は、`import(`、`import "x"`、`... from "x"` の 3 つしかない。この 3 つを trivia つきで全部読む
- **読み込み先の文字列を、読み込む側と同じように解読する**
  - エスケープ（`\uXXXX`、`\u{...}`、`\xXX`、`\n` など）と行の継続（LF、CR+LF、U+2028 / U+2029）を解読して、本当の行き先で判断する
  - 古い 8 進数のエスケープ（モジュールでは構文エラー）など、解読できないものは「追えない」として止める
- **読めない形は止める（fail closed）**
  - `import` / `export` / `from` のあとに閉じないコメントがあれば止める（読み込む側も構文エラーにする形）
  - 計算した `import()` は、コメントがあっても計算したものとして止める
- 生の文字列を読む方針は #219 のまま（コメントや文字列に読み込みを隠せない。コメントの中の読み込みも数えて、止める側に倒れる）
- import / export の句の中のコメントは、名前を読む前に取り除く（`{ a /* c */ }` は名前 `a`）

### 確かめたこと

- テストの中の合成の木（`J1 R1a:` のテスト）
  - J1 の再現そのもの。直接の参照の一覧も到達の一覧も変わらないので、名前の決まりだけが見つけられる
  - 行のコメントと改行、U+2028、コメント 2 つ、引数の前後のコメント、`["SupabaseLedgerBudgetGuard"]` での取り出し、`.then(({ ... }) => ...)`、複数行のコメント、handler で同じこと
  - コメントつきの計算した `import()`（変数、足し算、`join`、`${}`、閉じないコメント）
  - コメントつきの静的な読み込み（`from/* c */`、`import/* c */{...}/* c */from`、句の中の `/* } */`、`export/**/*/**/from`、`export * as ... from // c`、`import/* c */"..."`）
  - 新しい Edge のファイルが trivia つきで bridge を読む（到達で止める）
  - エスケープ（`_`、`\x5f`、`\u{5f}`）と行の継続（LF、CR+LF）を含む読み込み先。静的な読み込みも動的な読み込みも止める
  - 8 進数のエスケープ（追えないので止める）
  - trivia つきの `export *` の中継（到達で止める）
- 普通の読み込みは通る（`J1 R1: ordinary imports stay accepted`）。コメントつきの名前つきの読み込み、型だけの読み込み、`import(/* chunk */ "./x.ts")`、行のコメントを挟む `import()`、bridge が許可された名前をコメントつきで書き直す、を足した
- 本物のファイルでの比較（直す前 = #219 `be35cc93`。F6 の検査と H5 の検査を両方流す）: 結果は Report に書く

## 2. A1: 500 番台のエラーを「課金なし（0 円）」で記録していた（`errors.ts`）

### 何が問題だったか

- Anthropic の 500 / 502 / 503、OpenAI の 500 / 502 は、`maybeBilled: false` に分類されていた
- そのため、使用量 0（ZERO_USAGE）→ 台帳に `failed` / `measured` / 0 円で精算されていた
- 1 回しか送らなくなっても（#219）、別の操作として何度も呼ぶと、そのたびに 0 円で数えるので、費用の上限をすり抜けられた（J1 の再現: 上限 1.5 回分で 3 回送れた）

### どう直したか

- **「課金なし」と見なすのは、各 API が「リクエストそのものを断った」と文書で決めている HTTP ステータスだけ**
  - Anthropic: 400、401、402、403、404、413、429、529
  - OpenAI: 400、401、403、404、429、503
  - それ以外（500 / 502 / 503 / 504 とその他の 5xx、408 / 409 / 422 などの文書に無いステータス）は「課金された可能性がある」（`maybeBilled: true`）
- **決めるのはステータスだけ。エラーの種類名や文言では「課金なし」にならない**
  - たとえば 500 で `overloaded_error` や `rate_limit_error` と書いてあっても、「断った」にはしない。`SERVER_ERROR`、課金の可能性あり、送り直さない
  - 以前は種類名だけで `OVERLOADED` / `RATE_LIMITED` に分類し、送り直していた。いまは 529 / 429 のステータスのときだけ
  - 種類名で不確かさを増やす方向（`timeout_error` は常に課金の可能性あり）はそのまま
- 課金の可能性がある失敗は、使用量が分からないので、最大額で `unknown` / `upper_bound` として精算する。台帳の SQL は、この形（HTTP ステータスつき、トークン数なし、予約額以上）をすでに受け付ける（504 と同じ）。**DB / RPC / migration の変更は要らない**
- 変えていないもの
  - 実際の使用量が返った失敗（例: OpenAI の `status: "failed"` で使用量つき、拒否や途中で切れた出力）は、その使用量で精算する
  - 429 / 529 / OpenAI 503 は今まで通り 0 円で、`maxAttempts` の範囲で送り直す
  - 送り直さない決まり（#219）、モデルや provider の切り替えが無いこと、OpenAI の adapter の送る中身

### 確かめたこと

- J1 の再現（直す前は落ち、直した後は通る。scratch のテスト）
  - Anthropic 500 / 502 / 503、OpenAI 500 / 502: `unknown` / `upper_bound` / 最大額で精算される
  - 上限 1.5 回分の費用の枠で、500 を返す別々の操作を 3 回: 送るのは 1 回だけ
- リポジトリのテスト（`ambiguous_retry_test.ts`、`errors_test.ts`）
  - 500 / 502 / Anthropic 503 / OpenAI 500 / 502 で、送信 1 回、`unknown` / `upper_bound`、台帳の行に最大額と HTTP ステータス
  - 別々の操作で 500 / 502 を繰り返しても、共有の上限を超える分は送る前に断る（`COST_LIMIT`）
  - 429 / 529 / OpenAI 503 は 0 円の `failed` / `measured`
  - OpenAI の `status: "failed"` は、使用量があればその金額、無ければ最大額
  - ステータスごとの表（断ったステータスだけが課金なし）、種類名では課金なしにならないこと
- 古い決まりを固定していた F6 のテスト 2 件を直した: `anthropic_adapter_test.ts` の 19（500 の使用量は「不明」）と、`market_report_primary_test.ts` の失敗のテスト（500 は `unknown` で 0 円より多い）。どちらも送信 1 回・切り替え無しの確認はそのまま
- 市況レポート（`primary_both`）のテスト 324 件はそのまま通る。今動いている市況レポートでは、500 番台の失敗が 0 円ではなく最大額で台帳に残るようになる（deploy されたとき）。送る回数と失敗の扱いは変わらない

## 3. 残るリスク

- 読み込みの検査は CI の検査で、実行時の囲いではない。`eval` / `new Function` / `Worker` に渡す文字列、functions の外の設定（リポジトリ直下の `package.json` など）は見ない（#219 と同じ）
- コメントや文字列の中に `import(` と書いた説明があると、止める側に倒れる（いまの functions には無い）
- 「断ったステータス」の一覧は、各社の文書と、これまでの分類（`errors.ts` の冒頭）に基づく。provider が文書と違う動きをしたら、その分は分からない。実際の請求との突き合わせはしていない（NOT_VERIFIED）
- 500 番台が多い日は、台帳の残りが実際より早く減る（安全側）。費用の上限の調整は、運用で判断する
