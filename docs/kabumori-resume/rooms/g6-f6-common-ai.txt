## 2. アプリの機能・仕様・設計上の決定事項

### 2-1. 共通AI基盤の基本設計

OpenAI APIとClaude APIを、各アプリが直接個別実装するのではなく、共通のProvider層から利用する設計を進めた。

主要構成：

```text
かぶモリ / POSTONA
        │
        ▼
各アプリのAI利用処理
        │
        ▼
Consumer Bridge
        │
        ▼
共通AI Provider
        │
        ├── OpenAI API
        │
        └── Anthropic Claude API
        │
        ▼
利用量・料金・予算管理
```

目標は、アプリ固有処理と外部AI APIへの通信処理を分離すること。

ただし、**2026年10月17日時点で、POSTONAがこの構成へ本番接続されたわけではない。**

### 2-2. Provider設計

共通AI Providerでは以下を重視した。

- プロバイダーごとのAPI差異を吸収する
- 利用可能なAIモデルを明示的に制限する
- AIの実際の利用量を把握する
- 利用量が不明な場合も予算を過小評価しない
- タイムアウト後の安易な再送を禁止する
- 呼び出し元の認証・権限を検証する
- アプリ間のAI利用権限を分離する
- 既存OpenAI経路を不用意に変更しない

### 2-3. 利用料金管理

API呼び出しごとに利用量と費用を管理する設計を進めた。

重要な判断：

**失敗したAPI呼び出しを自動的に無料とみなしてはならない。**

HTTP 500・502・503などのエラーでも、外部AI側で処理が進み、課金が発生する可能性がある。

したがって、費用が確定できない場合は、

```text
unknown
upper_bound
```

などの状態を使用し、安全側の費用見積もりを維持する。

この修正はPR #219・#222系列で実施され、後続の限定レビューでは費用計上部分を再レビュー対象から除外した。

### 2-4. 二重送信・二重課金防止

重要な設計判断：

**タイムアウトしたからといって、同じ有料AIリクエストを無条件に再送しない。**

特に504や接続断は、外部側で処理が完了しているか不明な場合がある。

主な対策：

- operationIdによる処理識別
- 同一要求の重複実行防止
- 送信済み状態の管理
- 不明な結果を安全側で扱う
- 再試行可能な失敗と再試行禁止の失敗を区別する

ただし、**POSTONAの本番利用に必要な永続的な二重送信防止ストアは未実装**である。

オフラインモックテストのPASSを、本番DBによる永続的な重複防止の完成と混同しないこと。

### 2-5. API認証と利用権限

共通AI Providerを、権限のないEdge Functionや利用者が呼び出せないようにする方針。

設計上、次を区別する必要がある。

- 実際の利用者
- 利用者が所属するブランド
- 共通アカウントの利用権
- アプリごとの利用権
- システム処理
- Cronからの実行
- 認可されたAI機能

静的なimport検査も追加されたが、これは**CIの静的検査であり、実行時sandboxではない**。

そのため、本番権限境界のすべてを保証する仕組みとして扱ってはならない。

### 3-4. セキュリティ修正の経緯

Claude ProviderとBridgeの権限境界について、複数回の限定レビューと修正を行った。

重要な問題と対応は以下。

| 段階 | 発見・修正した内容 |
|---|---|
| #219 | 動的importによる権限検査回避、504再送問題の修正系列 |
| #222 | コメントを使ったimport検査回避、課金不明時の費用計上 |
| #231 | 文字列・コメントの誤認を避ける字句解析 |
| #234 | 正規表現と除算の誤判定に対する独立したrawEdges検査 |
| #237 | Unicodeエスケープされたimportキーワードの検出 |

特に問題となったのは、権限検査が本物の`import()`を見落とすケース。

例：

```ts
import("../ai_provider/mod.ts")
```

コメントや文字列を利用して検査をすり抜ける問題があった。

さらに、

```text
\u0069mport
```

のように、キーワードの一部をUnicodeエスケープした場合の見落としも確認された。

PR #237では、エスケープしたキーワードを独立して検査する処理を追加した。

追加処理：

```text
escapedKeywordEdges
```

これにより、従来の字句解析やrawEdgesと独立した検査経路ができた。

**ただし、PR #237の安全性がすべての入力に対して数学的に証明されたわけではない。**

L6ではソース修正完了として受け入れたが、本番導入の承認はしていない。

## 5. 未完成機能・未解決問題

### 5-1. POSTONAのClaude API接続

現在、POSTONAはClaude Providerへ接続されていない。

未完成：

- AI相談の実接続
- AI投稿文生成の実接続

- Anthropic送信に対応したプライバシー表示
- 本番デプロイ

### 5-2. 個人情報のAnthropic送信

PR #239の調査時点では、個人情報のAnthropic送信が既存ルールに抵触する可能性があった。

その後、このチャットでユーザーが次の方針を了承した。

**POSTONAのAI相談内容および投稿文生成に必要な情報を、Anthropicへ送信する方向で開発を進める。**

ただし、次の条件付き。

- 必要最小限の情報だけ送信する
- プライバシー表示・利用規約を整備する
- アプリや利用者間の情報混在を防ぐ
- 利用権・費用上限を実装する
- 本番切り替えは別途承認を得る

**この了承は本番送信の実行許可ではない。**

また、既存の「個人情報送信禁止」ルールの正式な修正がGitHubに反映されたことは確認していない。

将来の担当者は、実装前に最新ルールと今回のユーザー判断を照合すること。

### 5-3. 費用台帳

POSTONA用の費用管理には、追加の本番DB設計が必要。

特に以下を決める必要がある。

- 利用者単位の記録
- サービス単位の記録
- ブランド単位の記録方法
- 無料枠・有料枠
- 利用上限
- 課金不明時の最大費用見積もり
- Cronやsystem実行の費用帰属

本番DBのmigrationは別TASK・別承認が必要。

### 5-4. ブランドIDの不整合

POSTONAのブランドIDはUUIDではない。

確認された仕様：

```text
brands.id:
^[a-z][a-z0-9_]{1,40}$
```

利用者ワークスペース：

```text
u_ + md5の24文字
```

一方、共通AI台帳の主体はUUIDベース。

そのため、POSTONAのブランドIDをそのまま共通AI台帳のUUID欄に入れてはいけない。

ブランド単位の費用記録・利用権を設計する必要がある。

### 5-5. 永続的な二重送信防止

モック環境で同一operationIdの重複送信防止を確認した。

しかし、永続的な保存場所がまだ決まっていない。

必要なもの：

- DB上の一意性保証
- 実行状態の保存
- 再試行・タイムアウト時の状態遷移
- 課金不明状態の保持
- 並行実行時の安全性

特に予約投稿などのCron実行では重要になる。

### 5-6. Consumer Bridgeの許可設定

POSTONA側からBridgeを呼び出すには、現在のimport制限を変更する必要がある。

調査で判明した問題：

- F6側のisolation許可
- H5側のConsumer Bridge利用制限

両者を整合させる必要がある。

**F6だけの修正で解決しない。**

H5の所有境界と調整して、同時に設計すること。

### 5-7. 品質評価

Claude APIで生成した日本語の品質は未検証。

特に次の品質確認が必要。

- AI相談の自然さ
- 相談内容の正確性
- 日本語の読みやすさ
- 投稿文の自然さ
- SNSごとの文章品質
- 指示への忠実性
- JSON形式の遵守
- 生成時間
- トークン使用量
- OpenAIとの費用対効果

有料APIによる品質比較は、別途承認が必要。

```text
POSTONAのSNS投稿

共通AI Provider

Consumer Bridge

API利用量・費用管理

ユーザーDB
```

### 9-2. 無断変更禁止

以下は明示承認と安全確認が必要。

- production DB
- migration
- Auth
- RLS
- RPC
- SECURITY DEFINER
- Edge Functionの本番deploy
- Cron
- Secrets
- OAuth
- 外部APIへの実書き込み
- SNS実投稿
- 有料AI API呼び出し
- 本番モデル切り替え

新F6のPRは積み上げ関係にある。

```text

  ↓

  ↓
#205
  ↓
#219
  ↓
#222
  ↓

  ↓

  ↓

  ↓
```

マージ時はHEAD・base・差分・競合を必ず再確認する。

### 11-2. AIモデルの選択

PR #239では、Claude Haiku 5.5を候補とした。

理由：

- 比較的低い利用料金
- POSTONAの多数の短い生成処理に向く可能性
- 共通Providerのモデル選択で制御可能

ただし、**品質比較は未実施**。

| モデル | AI相談1回の上限見積もり |
|---|---:|
| Haiku 5.5 | $0.0044 |
| Sonnet系 | $0.089 |
| Opus系 | $0.18 |

投稿文生成は、Haiku候補で約$0.0012〜0.0019という見積もりが記録されている。

これらは当時の設計用の参考値であり、実測請求額ではない。

将来のAPI料金やモデル名は変更される可能性がある。

本番導入前に再確認すること。

### 11-3. モデルの切り替え

- 利用者ごとのAI使用量

- モデルごとの費用

- エラーによる不明費用
- 予算超過警告
- 利用制限
- 管理者向けの費用確認

これらは設計方針であり、完成済みの管理画面があるとは確認していない。
