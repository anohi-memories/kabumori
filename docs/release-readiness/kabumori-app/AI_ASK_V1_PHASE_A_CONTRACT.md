# 「AIに聞く」V1 — Phase A（対話UIと安全な接続契約）

- 作成: F1（`kabumori-f1-ai-ask-v1-phase-a-ui-contract-20261012`）／ 2026-10-12 JST
- 位置づけ: **Phase A はクライアントの画面と型付き契約だけ。サーバー・実プロバイダーには一切接続していない。**
  Phase B（サーバー実装・本番接続）は別 TASK・独立した Security レビュー・ユーザー承認のあと。
- 関連: 棚卸し `V1_GAP_INVENTORY_2026-10-12.md` の REL-09（「AIに聞く」の3入口が準備中画面へ）への対応の一部。

## 1. 製品の範囲（ユーザー決定）

- 「AIに聞く」を V1 に含める。**対象は、保有銘柄についての質問と、ニュース・市場の情報を踏まえた回答**。汎用チャットではない。
- 公開後に回すもの: 会話履歴の永続化、モデル選択、高度な投資推奨。
- 質問の例: 「今日の市況は？」「〇〇の下落理由は？」「自分の保有銘柄に影響するニュースは？」「ポートフォリオのリスクは？」
- **回答を裏付けられない最新価格・理由・ニュースは創作しない。** 根拠が足りなければ「確認できる情報が足りないため回答を控える」。
- 個別の売買の推奨はしない（`investment_advice` として丁寧に断る）。

## 2. 他機能との役割分離（G2 の個別分析との違い）

| | 個別AI分析（G2・PR143） | AIに聞く（本機能） |
|---|---|---|
| 形 | ボタンで依頼 → サーバーのジョブ → 完成したら通知。結果はレポート形式 | 質問 → 短い回答（同期に近い対話） |
| 入力 | 範囲（スコープ）の選択のみ | 自由文（最大300文字）＋範囲 |
| 内容 | 本人のポートフォリオ全体のレポート | 質問に答える短い説明（根拠つき） |
| 保存 | `personalized_analysis_results` に保存 | Phase B でも V1 は保存しない（履歴は公開後） |
| 入口 | レポート/分析の画面 | ホーム・メニュー・ポートフォリオ下の3入口 → `/ai` |

- 重複を避けるため、「ポートフォリオ全体の定型レポートがほしい」は個別分析、「これはどういうこと？」は AIに聞く、と画面の文言で分ける（Phase B の UI 仕上げ）。
- 実装の共有: G2 のジョブ/RPC パターン（本人を `auth.uid()` で決める、ゲートで OFF にできる、関数が無いときは「準備中」）を踏襲する。

## 4. 型付き契約（クライアント ⇄ サーバー）

### リクエスト `AskRequest`（バージョン 1）

```ts
{
  version: 1,
  question: string,        // 正規化済み 1〜300 文字
  scope: 'market' | 'holdings' | 'stock',
  tickerCode: string | null,   // scope='stock' のときだけ。4桁数字または3桁数字+英字
  clientRequestId: string,     // 冪等キー。再試行は同じ ID
}
```

- **含めないもの（意図的）**: ユーザー ID、保有銘柄、価格、ニュース本文、端末情報。サーバーが JWT からユーザーを決め、保有・ニュース・市場データを自分で（RLS の下で）読む。
- 質問の正規化: 制御文字・ゼロ幅/方向制御文字を除去、空白を1つに畳む、前後の空白を除く。文字数は **コードポイント**で数える。

### レスポンス `AskResponse`

```ts
| { status: 'answered', answer, keyPoints: string[0..5], sources: AskSource[],
    generatedAt: ISO|null, dataAsOf: ISO|null, usedHoldings: boolean }
| { status: 'refused',  reason: 'investment_advice' | 'out_of_scope' | 'insufficient_evidence' }
| { status: 'failed',   code: 'unavailable' | 'auth_required' | 'rate_limited' | 'budget_exhausted'
                             | 'network' | 'timeout' | 'server_error' }

AskSource = { kind: 'news'|'report'|'market_data'|'holding', title, asOf: ISO|null, ref: string|null }
```

- `ref` は **アプリ内の ID**（ニュース ID / レポート ID）だけ。外部 URL は返さない（アプリは外部リンクを開かない）。
- `answered` が事実を述べるなら `sources` は 1 件以上。無い場合は「出典なし（一般的な説明です）」と表示し、根拠つきに見せない。
- `generatedAt` / `dataAsOf` / `source.asOf` が `null` のときは、画面は **「不明」と表示**する。補完・推測はしない。

### 失敗コードと G6 のプロバイダーエラーの対応（Phase B の設計メモ）

| クライアントの `code` | 主な原因（G6 `AiErrorCode` / サーバー） | 再試行 |
|---|---|---|
| `unavailable` | ゲート OFF、関数なし、`BUDGET_DENIED`（機能停止） | しない |
| `auth_required` | JWT 無効・期限切れ（`AUTH` ではなく Supabase 側） | しない（再ログイン） |
| `rate_limited` | 本人の上限、プロバイダーの `RATE_LIMITED` | しない（待つ） |
| `budget_exhausted` | 日次の費用上限（台帳）、`CREDIT_EXHAUSTED` / `SPEND_LIMIT` | しない |
| `network` | 端末の通信失敗 | する |
| `timeout` | `TIMEOUT` / `DEADLINE_EXCEEDED` | する |
| `server_error` | `SERVER_ERROR` / `OVERLOADED` / `PROTOCOL` / `INVALID_JSON` / `SCHEMA_VIOLATION` | する |

- プロバイダーの生のエラーメッセージ・モデル名・トークン数・費用は、クライアントに返さない。

## 5. 認証・個人データ・分離（Phase B の設計ゲート）

1. **ユーザーの特定は JWT のみ。** リクエスト本文のユーザー ID は存在しない。サーバーは検証済みの `auth.uid()` を `AiSubject { kind: 'user', userId }` に使う（G6 の使用量台帳の帰属と同じ）。
2. **保有・ウォッチリストの読み取りは本人の行だけ**（RLS）。`service_role` を使う場合も、必ず検証済みの本人 ID で絞る。クロスユーザーの混入を、別ユーザー2人のフィクスチャで実テストする。
3. **外部 AI へ送る内容の最小化**: 質問文＋回答に必要な最小の文脈（保有なら銘柄・数量の概況に丸める等）。メール・ユーザー ID・端末トークンは送らない。保有情報を外部 AI に送る機能は、**プライバシーポリシーへの明記（REL-04）と、利用者への表示（`usedHoldings`）**が先。
4. **同意**: 保有情報を使う質問（`scope: 'holdings'` / 一部の `stock`）の初回に、何を送るかを説明して同意を取る設計を Phase B で決める（Phase A は未実装・未決定）。
5. **ログ**: 質問文・回答・保有情報を、通常のアプリログ・エラーログ・分析に残さない。台帳（G6）には費用・トークン・結果コードのみ。
6. **保存しない（V1）**: 質問・回答はサーバーにも端末にも履歴として保存しない。

## 6. 出典と鮮度

- 根拠にできる材料は、アプリが既に持つ **内容確認済みのニュース**、**保存済みの朝刊・大引け**、**保存済みの終値**、**本人の登録**に限る（新しい外部取得はしない）。
- 回答に使った最も新しいデータの時点を `dataAsOf` に入れる。複数の出典の時点がばらつく場合は最も古いものではなく、**画面には各出典の時点を個別に表示**（`source.asOf`）する。
- 保存済みの終値を使う場合は、基準日（例「10/6 終値ベース」）を回答に含める。「リアルタイム」とは言わない。
- 鮮度が古い・不明な根拠しかない場合は、断定せず「確認できる範囲では」と限定する、または `insufficient_evidence` で控える。

## 7. プロンプト注入・濫用への防御（Phase B）

- 質問文は **信頼しないデータ**。システム指示は固定、質問は `userContent` の区切られた領域に入れる。質問の中の「指示を無視して」等は指示として扱わない。
- ニュース本文・出典の文章も信頼しないデータとして引用領域に入れ、指示として実行させない。
- 出力は JSON Schema で縛る（G6 の `jsonSchema`）。自由なテキストをそのまま画面に出さず、スキーマ検証に通ったものだけを返す。
- 制御文字・長さはクライアントとサーバーの**両方**で検証する（クライアントだけを信用しない）。
- 範囲外（雑談・個別売買の指示・アプリと無関係）は `out_of_scope` / `investment_advice` で断る。

## 8. 費用・レート・トークン上限（Phase B）

| 項目 | V1 の方針（案・要決定） |
|---|---|
| 質問の長さ | 300 文字（クライアントで強制、サーバーで再検証） |
| 出力 | `maxOutputTokens` を機能ごとに固定（短い回答） |
| 本人あたり | 1日の回数上限と、直近1分あたりの上限（サーバー側で数える） |
| 全体 | G6 の予算ガード（`budget.ts`）と使用量台帳。上限到達時は `budget_exhausted`／機能を `unavailable` に落とす |
| 冪等 | `clientRequestId` 単位で1回だけ課金（再試行の二重課金防止） |
| タイムアウト | 1回の呼び出しの上限を決め、タイムアウトの課金は上限見積もりで計上（G6 の方針） |
| 緊急停止 | サーバー側のゲート1つで即 OFF（アプリは `unavailable` 表示に戻る） |

## 9. Phase B 受入基準（本番接続の前に満たすこと）

1. **Security レビュー（独立）**: JWT 起点のユーザー特定、RLS、クロスユーザー分離、プロンプト注入、ログへの個人情報の非混入。
2. **データ境界の実テスト**: 2ユーザーの実 SQL フィクスチャで、他人の保有・分析・出典が一切混ざらないこと。
3. **費用の上限**: G6 の台帳・予算に載り、日次上限・本人上限が効き、上限到達で止まること（変異テスト）。
4. **根拠の検証**: 出典なしの事実の断定・存在しないニュース ID・未来/不明の時点を、サーバーで弾くこと。
5. **断る挙動**: 売買推奨の依頼に `investment_advice` を返すこと（定型の回帰ケース集）。
6. **ゲート**: サーバーの状態が OFF のとき、アプリが `unavailable` の表示になり、送信できないこと。古いアプリでも同様。
7. **アプリ**: 実機 iPhone で、成功・断り・失敗・再試行・時刻不明の表示を確認（フィクスチャのサーバーまたは検証用環境）。
8. **プライバシー**: ポリシーとサポートページに、質問文・保有情報の外部 AI への送信と保存しないことを明記（REL-04）。
9. **運用**: 緊急停止の手順、費用の見張り、ユーザーへの障害表示（RUNBOOK）。

## 10. 依存と未決定事項（ユーザー/他スロットの判断）

- **G6（共通AI基盤）**: プロバイダー呼び出しは `supabase/functions/_shared/ai_provider` を使う前提。OpenAI/Claude のどちらを使うか（G6 は Claude 比較が既定 OFF の任意機能）は **未決定**。モデル選択はユーザーに出さない（公開後も未定）。
- **G5（共通アカウント）**: JWT・本人確認の土台。V1 は G5 の未マージ分に依存しない設計（現行の Supabase セッションを使う）。
- **G8/G9（ニュース・コスト）**: 「内容確認済みのニュース」を根拠にするための、ニュースの出典・時刻の整備（`news_id` の安定性）。
- **G2**: 個別分析との画面上の役割分担、通知の重複を避ける。
- **決定が要ること**: (a) V1 に載せる範囲（`scope` を3つとも出すか、まず `market` と `holdings` だけか）、(b) 1日の上限回数、(c) 保有情報を使う質問の同意の見せ方、(d) 3入口の文言（公開時に「準備中」を外すタイミングと、REL-09 の方針との整合）。
