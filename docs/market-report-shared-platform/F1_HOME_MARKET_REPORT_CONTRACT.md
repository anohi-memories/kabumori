## 1. いまのアプリが `get_app_market_report` から使う項目（既存契約のまま）

| 項目 | 使い方 |
| --- | --- |
| `status` | `completed` の回だけをホームの候補にする。`missing` / `not_ready` / `disabled` は候補に入れない（未完成の大引けを先に出さない）。 |
| `report_type` / `trading_date` | 回の識別と並び順（取引日が新しい回 → 同じ取引日なら大引け）。ホームから詳細へ渡す引数。 |
| `is_today` | サーバーの日本時間での「取引日が今日」。ラベル（日付を付けるか）の判定。端末の時計は「日付をまたいだ保持分を今日と呼ばない」ためだけに併用。 |
| `report_packet_id` | 公開済みの回の一意な ID。ホームから詳細へ `id` として渡す（UUID の形だけ受け取る）。種類・日付が一致すれば再公開（ID の更新）でも開く。 |
| `points_ja` | ホームのポイント。保存済みの `x_post.points_ja` をそのまま（空白を整え、最大 3 項目）。X と同じ文で、アプリ側で作文・補完・再生成しない。 |

ホームの更新は、画面フォーカス・引っ張り更新・アプリ復帰（60 秒以上あけて、市況のみ）。ポーリングは無い。1 回の更新で `get_app_market_report` を 2 回（朝刊・大引けの最新）呼ぶ（以前の個別レポート取得 1 回の代わり）。

## 3. 過去の回の一覧用の取得契約（提案。アプリ側は未実装・RPC は未作成）

既存の `get_app_market_report(p_report_type, p_trading_date)` は 1 日・1 種類ずつで、一覧は取れない（`market_report_cycles` 等の表はアプリから直接読めず、読ませない）。一覧を出すには、同じ公開境界を共有する読み取り専用の関数が必要。**勝手に新 RPC は追加していない。** 追加する場合の条件:

- 例: `list_app_market_reports(p_report_type text default null, p_limit integer default 30, p_before_trading_date date default null) returns jsonb`（`stable security definer set search_path = ''`、`authenticated` のみ実行可、`auth.uid()` 必須。`get_app_market_report` と同じ権限・ゲート）。
- **公開条件は `get_app_market_report` と完全に同じ**にする: `public_market_feed_enabled`、`report_status = 'completed'` かつ `current_report_packet_id is not null`。未完成・未公開・失敗の回を含めない。ゲート OFF なら `{status:'disabled'}`。
- 返す項目（公開してよいものだけ。本文や根拠は返さない）: `report_type`、`trading_date`、`report_packet_id`、`headline_ja`、`market_direction`、（あれば）`published_at`。ポイントを一覧に出すなら `points_ja`（最大 3 項目）も。
- 並び順: `trading_date` 降順、同じ日は `close` → `morning`（ホームの順序規則と同じ）。
- 件数制限: 既定 30・最大 62 程度（約 31 日 × 朝刊・大引け）。範囲は `get_app_market_report` と同じ「今日から 31 日前まで」。ページングは `p_before_trading_date`（その日より前）。
- 範囲外の日付は例外ではなく空配列にする（現状の `get_app_market_report` は範囲外の日付で `22023` を投げ、アプリは汎用エラーになる）。

## 4. ホームの順序判定を堅くする追加項目（提案）

- 現在の RPC の `generated_at` はレポート本文の生成時刻（`payload.generated_at`）で、**公開した時刻ではない**。再生成された朝刊が大引けより新しい `generated_at` を持ちうるため、順序には使っていない。アプリは「取引日 → 同じ日なら大引け」で決める（朝刊の後に大引けが完成する構造的な順序であり、時刻の推測ではない）。
- 公開の順序そのものをサーバーに決めさせるなら、次のどちらか:
  1. 返り値に `published_at`（サイクルの `completed_at` など、**その回を公開した時刻**）を追加する。
  2. もしくは、朝刊・大引けの最新のうち公開が新しい 1 件を返す `get_latest_app_market_report()` を用意する。ホームの RPC が 2 回 → 1 回になり、順序判定もサーバーに寄る。
- どちらも追加は任意。現状の規則で、朝刊完成 → 大引け完成 → 翌営業日の朝刊の切替はテスト済み（模擬サーバー）。

## 5. ゆめちゃんの考察（今回の必須外・見送り）

- 保存済みの `yume`（朝刊: `headline_ja`＝今日の予想／大引け: `review.text_ja`＝振り返り）は RPC で既に返っており、詳細画面には表示済み。
- ホームには載せていない。ヒーローのポイント欄は 2 行・1 項目 10.5pt の固定レイアウトで、保存済みの文を意味を変えずに短縮する方法がない（機械的な切り詰めはゆめちゃんの見解の趣旨を変えうる）。デザインを変えずに載せられる枠もない。
- 別 TASK 候補: ホームに「ゆめちゃんの今日の予想／振り返り」の小さな 1 行を足す。デザイン判断（枠・文字数）が先に必要。

## 7. レポートタブの共通市況化（PR #202 の追加コミット）

- レポートタブ（`src/app/(tabs)/reports/index.tsx`）を「最新の市況（朝刊・大引けのカード）→ 過去のレポート → 保有銘柄のAI分析 → 通知」に再構成した。カードはホームと同じ保存済みの共通レポート（`get_app_market_report` の朝刊・大引けの最新、RPC 2 回）から作る。取引日は回の日付をそのまま出し、完成・公開済み（`completed`）の回だけをカードにする。カードを押すとホームと同じ引数（type・date・id・strict=1）で指定の回の詳細へ。
- 過去の回の**一覧**用の関数が無いので、「過去の朝刊／大引けを日付で見る」は詳細画面の日付ナビを開く入口にした（最新の回の前の平日から。土日だけ飛ばす。祝日は分からないので飛ばさない）。一覧契約（3 章）が入れば、この入口を一覧に置き換える。
- **通知の契約は不足なし**: 設定は `alert_settings.morning_report / close_report`。共通の一斉通知（`20261012100000_market_report_broadcast_push_v1.sql` の対象判定）も同じ列を見る。タブの通知スイッチの文言を「共通の朝刊・大引けの通知」にしただけで、列・保存の挙動は変えていない。
- **F2 へ（確認事項）**: 旧個別レポートの通知（`enqueue_personalized_report_notification`）も同じ `morning_report / close_report` を見る。`allow_with_legacy_personalized_reports = true` のまま旧個別 Cron を再開すると、同じスイッチで共通と個別の通知が二重に届きうる（現在は旧 Cron OFF）。旧個別レポートを完全に止めるなら、通知側で個別を別のスイッチに分けるか、個別の予約を止める判断が要る（アプリ側は変更していない）。
- 旧個別定時レポートを前提にしていた文言（「平日の朝8時半ごろに届きます」「平日の17時すぎに届きます」「あなたのレポート」「登録した保有・監視銘柄に合わせて…」）と今日の個別カードは削除した。個別レポートの詳細・オンデマンドのAI分析・通知設定・DB は削除していない（「これまでの個別レポート」「保有銘柄のAI分析」の見出しの下に残した）。
- 保有銘柄タブ・銘柄詳細にある個別レポートへの導線（保有銘柄向けの影響表示）は、保有銘柄の機能として今回は変更していない。
