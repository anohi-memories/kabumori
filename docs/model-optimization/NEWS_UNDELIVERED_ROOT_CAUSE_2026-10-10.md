# 重要ニュースが利用者に届かなかった原因の分析（Phase 5 / 2026-10-10 JST）

担当: B（ニュース・API最適化）。有料API呼び出し・本番変更・schema変更・安全ゲートの変更・PR #115/#116/#117 への変更・merge・deploy は一切していない。
本番DBは SELECT のみ（件数・状態・短い判定理由。TDnet の本文はローカルの集計にだけ使い、保存していない）。TDnet の 403 は迂回していない。

分析期間は 2026-09-10 00:00〜2026-10-10 00:00 JST に作成された AI 判定済みの候補 2,213 件（重要以上 405、no_post 1,808）。重複として判定前に除かれた 70 件は含まない。
再現用のSQLは `tools/provider-compare/scripts/export_{gate_breakdown,generation_outcomes,delivery_channels,ingestion_gaps,tanshin_rows,status_overview}.sql`、集計は `scripts/phase5_report.ts`、結果は `docs/model-optimization/phase5_report_2026-10-10.json`。

## 1. 結論

1. **未配信は一つの原因ではなく、段階ごとに別の原因が重なっている。** 取り込み（本文が空・表の当期行の欠落）→ 判定（情報十分性ゲート）→ 生成（Fact・Voice）→ 配信先（X・アプリ・プッシュ）の順に、それぞれ別の数字になる。
2. **ゲートは no_post の 22%（402/1,808）を作っている。** Sol を通った判定 636 件の 63% がゲートで no_post になった。ゲート前の重要度は保存されないが、理由文の言い回しから「重要だが確認できない」に読めるものが約 44〜53 件（11〜13%）ある。1日あたり約2件で、確認待ちとして人が見られる量。
3. **「生成失敗 47%」は本番全体の失敗率ではない。** 期間の前半に集中した値で、直近 7 日（10/3〜10/9）は **23.1%（39/169）**、直近 3 日は 21.1%。分母が「全判定」なら 4.5〜8.9%。
4. **失敗の主因は期間で入れ替わっている。** 9/10〜9/18 は年の欠落が 59%（63/107）、直近 7 日は数値・Voice・欠落・同一性に分散し、PR #116 が直接効くのは 39 件中 6 件（15%）、部分的に効くのが 7 件（18%）。
5. **「Xに出なかった」と「アプリで見えない」は別。** 生成に失敗した 196 件のうち 152 件（78%）はアプリのニュース一覧に載りうる状態で、重要以上と判定された 405 件のうち X 配信は 208 件（51%）、アプリ掲載可能は 349 件（86%）。
6. **取り込みの問題は独立した課題として 4 つある。** 決算短信の当期行の欠落（確認できた 143 件の 90%）、日銀 PDF の本文が全件空（71/71）、FOMC声明が表題のみ、名証系の開示の取り込み漏れの疑い。

## 2. 判定ゲートの調査

### 2.1 どこで no_post になるか
`importance_judgement_logic.ts` の `judgeCandidateWithEscalation` は、Luna を呼び、Luna が Sol を要求したら（`needs_sol`・確信度 0.7 未満・most_important 候補・Fact が needs_review のいずれか）Sol を呼ぶ。その結果の最終判定について、次のどちらかなら重要度を **no_post に強制**し、理由文の末尾に固定文を足す。

- (a) 最終の `fact_check_status` が `passed` でない
- (b) Sol が必要だったが実行されなかった（`sol_escalation_enabled` が false）

Luna または Sol の呼び出し自体が失敗した場合は、例外になって候補は `pending_judgement` のまま残り、再試行される（no_post にはならない）。

### 2.2 5 区分の件数（期間内、保存データから復元できた範囲）

| 区分 | 件数 | 復元の根拠 |
|---|---|---|
| モデル自身が no_post（Fact は passed） | 1,406（Luna 最終 1,363 / Sol 最終 43） | 理由文にゲート文が無く、`fact_check_status = passed` |
| モデルは重要以上だが Fact が needs_review → ゲートで no_post | 402 のうち一部 | 重要度の元の値は保存されない。理由文の言い回しで 44 件が『重要だが確認できない』、9 件が混在 |
| Sol が必要だったが実行できなかった | **0** | `sol_escalation_enabled = true`（2026-09-10 17:53 JST から）。この期間は発生していない |
| 最終ゲートで no_post へ変更（上の2行を合わせたもの） | 402（no_post の 22.2%） | 理由文のゲート文 + `escalated_to_sol` + `fact_check_status = needs_review` |
| その他の停止 | 重複 70（判定前）/ ready_for_publish 1（9/10 から滞留）/ 判定待ち 0 | `status`・`duplicate_of` |

- ゲート 402 件はすべて Sol が実行された後（`escalated_to_sol = true`）。Luna が `FACT_NEEDS_REVIEW` を出したのが gpt-6 世代の 303 件中 301 件で、Sol も同じ判断をした形。残る 2 件は『最重要候補』として昇格し、Sol が needs_review を返した。
- Sol を通った 636 件の内訳は、配信対象（重要以上）191 件、Sol 自身が no_post 43 件、ゲート 402 件。
- 世代が古い 99 件（gpt-5.6-sol）は、昇格理由が使用量台帳に残っていない。

### 2.4 観測性の改善案（設計のみ。実装も schema 変更もしていない）
ゲートそのものは変えない。ゲートが適用された時点で、メモリ上にある 3 つの出力から次の記録を作り、保存する案。

```
JudgementTrace (version 1)
  luna:       { importance, factCheckStatus, confidence, needsSol }
  escalation: { required, reasons[], solEnabled, ran, notRunBecause: "not_required" | "disabled" | null }
  sol:        { importance, factCheckStatus, confidence } | null
  gate:       { applied, trigger: "fact_not_passed" | "sol_required_not_run" | null,
                preGateImportance, preGateFactStatus }
  final:      { importance, factCheckStatus }
  missingInformation[]: body_empty | numbers_missing | current_period_missing | inconsistent_summary
                       | scale_unknown | identity_unconfirmed | single_source | source_unclear
```

| 依頼された観測項目 | 記録先のフィールド |
|---|---|
| ゲート前の重要度 | `gate.preGateImportance`（Sol が走った場合は Sol、走らない場合は Luna の出力） |
| ゲート前の Fact 状態 | `gate.preGateFactStatus` |
| ゲート適用理由 | `gate.trigger`（Fact 未通過 / Sol 必要だが未実行）と `escalation.reasons` |
| 最終重要度 | `final.importance` |
| 必要な追加情報の種類 | `missingInformation[]` |

- 実装は `src/gate_analysis.ts` の `buildJudgementTrace` に型と生成関数を置き、本番の `judgeCandidateWithEscalation` の出力との組合せ（Luna × Sol × 設定 144 通り）で、記録がゲートの結果と矛盾しないことをテストした。**この型は本番から使われていない。**
- 保存先の候補は (1) 候補テーブルへの jsonb 列、(2) 別テーブル（candidate_id, version, trace, created_at）。(2) は候補テーブルを肥大化させず、古い行を捨てやすい。いずれも schema 変更を伴うため、承認と C2 レビューの対象。
- 現状でも使える暫定策: 理由文の言い回しからの推定（`reasonSignal`、`inferMissingInformation`）。これは**再ラベルには使わず、確認待ちキューの大きさを見積もる用途に限る**。
- **確認待ちキュー（暫定基準 6）**: ゲートが働いたうち、重要の言い回しがあるもの（約 44〜53 件/30 日）を、配信せずに人が見る一覧として観測する。公開安全性は変わらない。

### 4.2 差が生じる理由
1. **期間が最大の要因。** 30 日の 48.4% は、前半の失敗率 72%・57% の期間に引き上げられている。直近 7 日は 23.1%。同じ定義 A でも、期間が違えば倍の差になる。
2. **評価セットの除外は小さい。** 212 件を除いても 48.4% → 47.1%。Phase 4 の 155/329 が高いのは、期間の違いであって、除外の偏りではない。
3. **分母の取り方で 4.5%〜48%。** 『重要以上』を分母にするか、『全判定済み』にするかで約 5 倍。X の配信率に近いのは前者。
4. **重複・状態の定義はほぼ影響しない**（A・B・C が 48.4〜48.5%）。重複は判定前に除かれている（70 件）。
5. **A 担当の Preflight の数値は、このリポジトリ・PR から見つけられなかった。** 下記を確認すれば同一条件で突き合わせられる。
   - 期間の基準（作成日・判定日・生成日）とタイムゾーン、末日が 10/9 か 10/10 の途中か
   - 分母（重要以上のみか、no_post を含むか、TDnet のみか）
   - 状態の集合（published・generation_failed 以外に ready_for_publish 等を含むか）
   - 重複と評価セットの扱い
   - 『失敗』が最終状態か、一度でも失敗した試行か（再試行を数えるか）

**47% を本番全体の失敗率として扱ってはいけない。** 最新の運用の実態に近いのは、直近 7 日の約 23%（定義 F）。
