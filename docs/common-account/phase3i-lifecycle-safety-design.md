| # | Phase 3h の観測（ローカル OSS、1 回ずつ） | 区分 |

## 2. 観測を、どの層で保証できるか

「層」は、そのリクエストの可否を**自分たちが決められる**場所のこと。

| 層 | 自分たちが決められるか | この層で保証できること |
| --- | --- | --- |
| アプリの権限（Edge Function、SECURITY DEFINER の書き込み関数） | 決められる（自分たちのコード） | 書き込み関数の先頭でライフサイクルの状態を確認する（T13 ガード）。人の token で動く Edge Function が、毎回、状態を確認する |
| データベースのポリシー（RLS、述語関数） | 決められる（migration で入れる） | PostgREST の直接の書き込みと Storage API の書き込みを、**token の鮮度ではなく、今のライフサイクル状態**で拒否する。これが F2・F4 に対する本体 |
| プロバイダ連携（Apple、Threads、X） | 部分的に（型付きの結果で） | 既知の識別情報の grant の失効を、結果（成功 / 失敗が確定 / 不明）つきで記録する。**遅れて現れた識別情報の grant は失効できない場合がある** |
| ライフサイクルの状態遷移（Phase 1〜3a） | 決められる | 閉鎖の開始（freeze）、操作の耐久記録、リース、外部ステップの意図と結果、読み戻しつきの完了 |
| Storage の掃除（Storage API） | 決められる | 所有オブジェクトの一覧 → 削除 → 再一覧の反復と、孤児スイーパー |
| **Supabase Auth（GoTrue、managed）** | **決められない** | BAN・セッション失効・フックは**補助**。F1〜F3・F7 のとおり、境界にはならない |

したがって方針は次のとおり。**Auth に「識別情報の変更を止めさせる」ことを諦め、自分たちのデータ面に「閉鎖後は誰の書き込みも通さない」境界を置き、遅れた識別情報は検出して突合する。**

## 3. 不変条件

### 3.1 主張するもの（I1〜I7）

| # | 不変条件 | 境界（§4） | 主張の条件 |
| --- | --- | --- | --- |
| I1 | 閉鎖の freeze が確定した後、その主体のサービスデータへの書き込みは、**freeze の前に始まった文を除いて**受理されない（ガードやポリシーを通る全経路） | B1 + B2 + B3 | `state_predicate`、`writer_guard`、`person_token_edge_checks` が attested |
| I2 | token の古さ・BAN・フック・セッションの新旧は、許可の根拠にならない。freeze 後に発行された token（F2）も、更新された token も、同じく拒否される | B1 + B3 | I1 と同じ |
| I3 | freeze の確定後に、その主体の Storage オブジェクトは作られない | B4 | I1 に加えて `storage_write_policy` が attested |
| I4 | 閉鎖が「完了」と記録されるのは、**削除の後に、判定と同じ時点で読んだ**事実（ユーザー不在、サービスデータ残り 0、Storage 残り 0、遅れた識別情報の監査 0、プロバイダの結果が確定）がそろったときだけ | ロジック（`decide`） | 常に |
| I5 | 一度しか使えない外部ステップ（Apple の認可コード、Auth の削除）は、再実行されない。曖昧な結果は読み戻しだけを行う | ロジック + Phase 3a の耐久的な意図 | 常に |
| I6 | 削除の前に、既知のすべての識別情報について、プロバイダの結果（失効済み / リモートでは未確認 / 適用外）が記録される。不明・失敗が残る間は削除しない | ロジック + アダプタ | 常に |
| I7 | 所有者がいなくなった行・オブジェクトは、いずれ検出され、掃除される | B5 | `orphan_sweeper` が attested |

## 4. 強制境界（B1〜B6）

名前は提案であり、現存を主張しない。

### B1 状態述語（データベース）— `state_predicate`

- 提案: `private.account_lifecycle_write_allowed(p_user_id uuid) returns boolean`（SECURITY DEFINER、`search_path=''`、所有者のみ EXECUTE）。
- 内容: `common_accounts.status = 'active'` かつ対象サービスの `service_entitlements.status = 'active'`。`auth.uid()` を使い、引数の他人 ID は拒否（T13 と同じ）。
- **ロック形式にする**: `select … from public.common_accounts … for key share`。
  - freeze（Phase 1 の `account_lifecycle_lock` が `common_accounts` を `FOR UPDATE`）は、書き込み中のトランザクションの完了を待つ。これで「freeze の前に始まった文」が残る窓を作らない。
  - ロックしない `STABLE` な述語だと、READ COMMITTED の文が `active` を見たまま freeze 後にコミットできる。これは invariants_test の探索で実際に見つかった窓（§9）。
  - 注意点: `FOR UPDATE` は、`KEY SHARE` が連続すると待たされうる。freeze には `lock_timeout` と有限回の再試行を付ける。**これはローカルの PostgreSQL での実証がまだ必要**（Phase 1/2 と同じ形式の 2 セッション競合テスト。別 TASK）。
- 適用先: 閉鎖の対象となる全サービステーブルの `INSERT` / `UPDATE` の `WITH CHECK`。範囲は「サービスフットプリント」の一覧（Phase 1 の `account_lifecycle_footprint`）と一致させる。
- 読み取りは対象外（閉鎖中の本人が状態を確認できるようにするため）。

### B2 書き込みガード（アプリの権限）— `writer_guard`

- PR #121 の `private.account_lifecycle_assert_active_service_write(uuid, text)`（T13）。SECURITY DEFINER の書き込み関数が、先頭で呼ぶ。
- B1 と同じロック順（login → account → entitlement）。未配線・未適用。

### B3 人の token で動く Edge Function の確認 — `person_token_edge_checks`

- 対象: `account-delete`、`social-mobile-account-delete`、`x-oauth-connect-user`、`x-test-post`、`social-mobile-consult`、`social-mobile-publish-setting`、`social-mobile-brand-dry-run`、`social-mobile-history-learning`、Threads の begin / complete / 手動投稿。
- 要件: **JWT をローカルで検証するだけでは足りない**（F4）。書き込み・外部呼び出しの前に、ライフサイクルの状態を service role の RPC で確認し、取得に失敗したら拒否する（fail closed）。
- AI 呼び出し（G6）も同じ。台帳の予約の前に確認する（§11 の D5）。

### B4 Storage の書き込みポリシー — `storage_write_policy`

- `storage.objects` の `INSERT` / `UPDATE` ポリシーに、B1 の述語を加える。
- **現状はリポジトリの migration に無い（U1）。** バケットとポリシーを migration として管理し、`pg_policy` の読み戻しで確認できるまで attested にしない。

### B5 孤児スイーパー — `orphan_sweeper`

- 所有者が存在しない行・オブジェクトの検出と掃除。外部キーが無いテーブル、サービスロールのジョブ、削除後に到着した遅い書き込み（F4・F6）への補償制御。
- 失敗時に安全側に倒す（`findOrphans`）: 所有者の一覧が不完全または空なら実行しない（全削除の事故を防ぐ）。作成から猶予時間が経つ前の行は対象外。
- Storage は Storage API 経由で削除し、再一覧で確認する（SQL では消さない）。
- 生の ID を保持せずに動く: 所有者の存在確認（反結合）で検出する。件数と、ハッシュ化した識別子だけを記録する。

### B6 境界マニフェスト — 確認の記録

- 境界ごとに「関数の本体ハッシュ、所有者、ACL、ポリシーの存在、対象テーブルの一覧、版」を読み戻して、**審査済みのマニフェストと一致するときだけ `attested`**。読めなければ `unknown`、無ければ `missing`。
- 閉鎖の開始時に毎回確認する。古い確認は使わない。

## 5. 段階的な閉鎖プロトコル

実装は `decide(facts)`（`protocol.ts`）。純粋関数で、**事実だけ**から次の動作を決める。再開は、同じ事実から同じ決定を再導出することで実現する。

| 段階 | 目的 | 操作（Phase 3a 等の既存部品） | 読み戻しの要件 | 失敗・不明のとき |
| --- | --- | --- | --- | --- |
| P0 準備 | 始めてよいか | 読み取りのみ。マニフェスト、アカウント状態、直近のサインイン（600 秒以内） | 境界が attested、状態が active、再認証が fresh | **STOP**（`BOUNDARY_UNPROVEN` / `REAUTH_REQUIRED` / `ACCOUNT_LOCKED` / `ACCOUNT_STATE_UNKNOWN`）。何も実行しない |
| P1 freeze | データ面の境界を有効にする | `begin_common_account_deletion`（状態 → `deleting`、操作を開く） | 状態が `deleting`、操作が open | 確定が不明なら状態を読み戻す。読めなければ STOP |
| P2 封じ込め | 流入を減らす（**保証ではない**） | セッション失効 → BAN。この順序（BAN 後は logout が拒否されるため） | 結果を記録するだけ | **失敗しても続行**する。必須でも十分でもない |
| P3 サービス掃除 | サービスデータの除去 | Kabumori の退会、X の saga、Threads のアダプタ | 残りを再読み込みして 0。有限回で収束しなければ突合 | `CLEANUP_NOT_CONVERGING` / `UNKNOWN_AFTER_START` |
| P4 プロバイダ | 既知の識別情報ごとに結果を確定 | Apple は型付きの結果（Phase 3a）。Threads は `local_removed_remote_unverified` など | 全プロバイダが「失効済み / 未確認 / 適用外」 | 保留・失敗は再試行（上限あり）。不明は `PROVIDER_UNRESOLVED` |
| P5 Storage | 所有オブジェクトの除去 | 一覧 → 削除（Storage API）→ 再一覧 | **連続 2 回の 0 件**。「読めない」は 0 ではない | 収束しなければ突合 |
| P6 決定 | 削除の直前の判断 | 排他ロックの下で、識別情報のスナップショットと残りを取る（Phase 3a の managed intent） | 現在の識別情報 ⊆ スナップショット。増えていたら P4 に戻る（有限回） | `CLEANUP_NOT_CONVERGING` |
| P7 Auth 削除 | 削除は 1 回だけ | Admin API の削除 | 応答が失われたら**読み戻しだけ**を行う（再実行しない） | 事前に失敗が確定した場合のみ再決定（上限あり）。`DELETE_NOT_CONFIRMED` |
| P8 検証と完了 | 完了を事実で確定 | 削除後に、判定と**同じ時点で**読む | ユーザー不在、残り 0、Storage 残り 0、遅れた識別情報の監査 0、プロバイダの結果が確定 | `LATE_IDENTITY_DETECTED` / `RESIDUE_AFTER_DELETE` / `LOGIN_REMOVED_WITHOUT_INTENT` |

要点:
- **P2 は P3 以降の前提ではない。** `containment` が失敗でも、判定は変わらない（テスト済み）。
- **時間は判定に使わない。** `elapsedSinceFreezeSec` を事実に含めているが、`decide` は読まない（テストで、任意の経過時間で同じ決定になることを確認）。

## 6. 競合と遅いコールバックの扱い

| 経路 | 起こりうること | 受け止める境界 | 残るもの |
| --- | --- | --- | --- |
| 手動連携（開始後に閉鎖）F1 | 完了して識別情報と新セッションができる | データ面は B1・B3 が拒否（I1・I2）。識別情報はスナップショット（P6）か、削除後の監査（P8）で検出 | 識別情報そのものは止められない（N1）。プロバイダ grant は失効できない場合がある → 突合 |
| 自動連携の処理中 F3 | BAN や freeze の後に識別情報がコミットされる | 同上。P6 の再スナップショットで既知化できる。削除の直前以降の分は P8 の監査で検出 | 同上 |
| コード交換でのセッション発行 F2 | BAN 済みでもセッションと token が発行される | B1・B3（状態で拒否）。セッションの失効は衛生であって境界ではない | token 自体の発行は止められない（N2） |
| 古い token での書き込み F4 | PostgREST・Storage が受理する | B1（RLS）、B4（Storage）、B2（書き込み関数） | 述語が無いテーブル・バケットは B5 で検出・掃除 |
| freeze の前に始まった文 | freeze 後にコミットされる | B1 のロック形式で、freeze が待つ（I1 の「除く」を、実質ほぼ空にする） | 述語がロック形式でない書き込み口 → P8 の読み取りとスイーパー |
| 削除後に届く書き込み | 外部キーが無い表に、削除済み ID の行が作られる | B1（アカウント不在は拒否）、B5 | ゲートされない経路 → B5 |
| 閉鎖中の Threads の OAuth 完了 | コードを交換して資格情報を保存しようとする | B2 のガードで拒否。使い捨てコードは再送しない | 新しい接続フローが必要（契約どおり） |
| 閉鎖中の AI 呼び出し（G6） | 利用者の内容を保存する | B3 の確認で予約前に拒否。進行中の分は確定してよいが、内容は保存しない | 台帳の user_id の扱いは §11 D5 |
| フックの障害 F7 | 全員のサインインが 500 | **閉鎖プロトコルはフックに依存しない** | フックを閉鎖の手段として採用しない（推奨） |
| 応答が失われた Auth の削除 | 適用されたかが不明 | P7 の読み戻し | 読めなければ突合 |

## 7. セッション・token の鮮度

- 閉鎖を**始める**ときだけ、人の直近のサインイン（600 秒以内、Phase 3a の C1）を要求する。
- 以後は、再開・突合は耐久的な操作記録（リース、意図）に基づく。人の token は要らない。
- freeze の後は、**どの token も**（古い、更新された、BAN 後に発行された）状態で判定する（I2）。token の有効期限、BAN、フック、`jwt_expiry` の短縮は、安全の根拠として使わない。
- PostgREST が期限切れ直後の JWT を数秒受理する（F5）ことは、B1 が状態で判定するので影響しない。

## 8. データアクセスの制限

- 書き込み: B1（ポリシー）、B2（書き込み関数）、B3（Edge Function）。
- 読み取り: 閉鎖中も、本人の状態確認（閉鎖の進行表示）のための読み取りは許可する。サービスデータの読み取りの制限は主張しない。
- サービスロールのジョブ（push、レポート、ニュース）: 閉鎖中・閉鎖済みの主体を対象から外す。**外せない経路は B5 が補償する**（このため B5 は常に必須）。

## 9. 識別情報の突合と、探索で見つかった指摘

1. P4: 既知の識別情報ごとに、プロバイダの結果を確定する。
2. P6: 排他ロックの下で、識別情報を再度読み、増えていれば P4 に戻る（有限回）。
3. P8: Auth の削除の後は識別情報の行が消えるので、**監査ログ**（`identity_linked` の記録は削除後も残る、F9）から、スナップショットより後の連携を数える。1 件でもあれば `LATE_IDENTITY_DETECTED` として突合に回す。
   - 監査ログが読めない・保存されない設定なら、この検出は成り立たない（U3）。その場合、遅れた識別情報の grant は「不明」として扱い、`RECONCILE` にする。

**オフラインの探索で見つかった設計上の指摘**（`invariants_test.ts`、約 8,800 通りの割り込みの組）:
- 削除後の検証結果を**キャッシュ**すると、検証と判定の間に、freeze の前に始まった書き込みがコミットされ、`COMPLETE` が残りを見逃す（負の対照のテストで再現）。
- 契約: **検証の事実は、判定と同じ時点（同じスナップショット）で読む。** 実装では、完了の記録を、残りの再確認と同じトランザクションで行う（Phase 3a の `complete_common_account_deletion` が既に行っている形）。
- 完了の記録の後に届くものは、原理的に防げない。B5 が検出する。

## 10. 曖昧な結果、ロールバック、再開、冪等性、STOP

### 曖昧な結果

| 結果 | 次の動作 |
| --- | --- |
| Auth の削除の応答が失われた | 読み戻しのみ。適用済みなら P8 へ、未適用と確定したら再決定（上限あり） |
| freeze のコミットが不明 | アカウント状態を読み戻す。読めなければ STOP |
| プロバイダの結果が不明 | 再実行しない。`PROVIDER_UNRESOLVED` として突合 |
| Storage の一部だけ削除された | 再一覧して残りを再削除。連続 2 回 0 件まで |
| 事実が読めない | 開始前は STOP、開始後は突合。進めない |

### ロールバック

- 閉鎖の取り消し（abort）は、**最初の破壊的な掃除（P3）の前**までに限る。以降は前進のみ（完了するか、突合）。
- P7 の後は戻れない。

### 冪等性と再開

- ステップは `(operation_id, step, 対象)` で一意。外部の一回限りの操作は、実行前に意図を耐久的に記録し、結果は型付きで記録する（Phase 3a）。
- 再開は事実の再導出。`decide` は純粋なので、クラッシュ後も同じ事実から同じ決定になる（テスト済み）。

### STOP と突合の一覧

| コード | 種類 | 発生条件 |
| --- | --- | --- |
| `FACTS_INVALID` | STOP | 事実の形が不正 |
| `BOUNDARY_UNPROVEN` | STOP | 必須の境界が attested でない（どれが未確認かを返す） |
| `ACCOUNT_LOCKED` / `ACCOUNT_STATE_UNKNOWN` / `LIFECYCLE_INCONSISTENT` | STOP | 状態が閉鎖に適さない |
| `REAUTH_REQUIRED` | STOP | 直近のサインインが無い |
| `LOGIN_REMOVED_WITHOUT_INTENT` | 突合 | 別の経路でログインが消えた（運用者、管理画面、X の SQL 削除） |
| `LATE_IDENTITY_DETECTED` | 突合 | 削除後の監査に、スナップショット以降の連携がある |
| `RESIDUE_AFTER_DELETE` / `CLEANUP_NOT_CONVERGING` | 突合 | 掃除が有限回で収束しない |
| `DELETE_NOT_CONFIRMED` | 突合 | 削除が確認できない |
| `PROVIDER_UNRESOLVED` / `UNKNOWN_AFTER_START` | 突合 | プロバイダの結果、または事実が不明 |

## 12. オフライン回帰テストが示すこと、示さないこと

`tools/common-account-lifecycle-safety/`（実行: `deno test --no-config --allow-read tools/common-account-lifecycle-safety/`）。合成データのみ。ネットワーク・環境変数・ファイルの書き込みなし。

**示すこと（提案した判定ロジックについて）**
- 境界が確認できなければ、閉鎖を開始しない（STOP）。何の効果も実行しない。
- 時間は判定に使われない。BAN・フック・待機は、判定を安全側にも危険側にも動かさない。
- 曖昧な削除の応答では、読み戻ししか行わない。単回用の外部ステップを繰り返さない。
- 完了は、削除後の事実がそろったときだけ。遅れた識別情報と残りは、必ず突合になる。
- F1〜F4・F6・F7 を、攻撃側の動作としてモデル化し、2 つまでの割り込みを 12 の判定点に挿入する全組合せ（約 8,800 通り × 3 構成）で、不変条件が保たれる。
- 負の対照: 境界が無いと F4 が再現する。素朴な閉鎖（BAN → 掃除 → 削除 → 完了）は、同じ世界で不変条件を破る。
- ミューテーション 32 件（境界・事実・時間・封じ込め・掃除・プロバイダ・削除・検証・ゲート・スイーパー・モデル）をすべてテストが検出する。

**示さないこと**
- GoTrue・PostgREST・Storage・managed Supabase の実際の挙動。モデルは Phase 3h の観測の写しにすぎない。
- B1〜B6 の実体の正しさ（ロックの順序、飢餓、性能、述語の評価）。実装の後に、ローカルの PostgreSQL で別途証明する。
- 本番の準備状況。マニフェストの確認は実行時の読み戻しで行う。
