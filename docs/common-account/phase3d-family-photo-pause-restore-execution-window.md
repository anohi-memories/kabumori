## 0. 前提と、変わらない約束

- **無料プランのみで行う。** 有料プランへの変更やアドオンの購入はしない。費用が少しでも発生する見込みなら中止する。
- 利用者が受け入れたのは、**実際の検証期間中だけ**、家族写真アプリ（`anohi-memories`）を最長でおよそ 2〜3 日止めること。検証の準備中には止めない。
- **復旧が最優先。** 検証の途中でも、復旧の期限・異常・不確かさがあれば、検証を打ち切って復旧に移る。
- 自動のタイマーによる無人復旧は約束しない。「2〜3 日で必ず戻る」とも約束しない。
- **止めない・使わないもの**
  - 本番のかぶモリ / POSTONA（`stock-x-autopost`）は、どんな場合も一時停止しない。
  - 過去の停止中プロジェクト `common-account-gateb-20261005` は、再開も流用もしない。新規で、中身が空の使い捨てプロジェクトだけを使う。
- **段階ごとの承認**: 写真アプリの一時停止、使い捨てプロジェクトの作成、破壊的な実験（実行ごと・実験ごと）、E7、E11 は、すべて別々の承認が必要。
  - 無料プランで進めるという一般的な了承は、E2〜E12 の削除・BAN を無制限に許すものではない。

### 公開ドキュメントで確認した Supabase の制約（2026-10-10 に閲覧。実際の窓の時点で再確認する）

- 無料プランで同時に active にできるのは **2 プロジェクトまで**。一時停止中・削除済みのプロジェクトは数に入らない。
  - 出典: [Pricing](https://supabase.com/pricing)、[Project Pausing](https://supabase.com/docs/guides/platform/free-project-pausing)
- 一時停止した無料プロジェクトは、Dashboard の「Resume project」で再開でき、**データと設定を含めて元の状態に戻る**とされている。
  - 再開できる期間: 現行の文書では停止から 1 年。2024 年の changelog は 90 日としていた。
  - 期限を過ぎると、バックアップのダウンロードしかできなくなる。
  - 古いバックアップは、プラットフォームの変更と互換性がなくなることがある。
- **公開文書に書かれていなかったこと**（窓の時点で確認する。確認できなければ不明として扱う）
  - 再開にかかる時間
  - Storage オブジェクト（写真）、Auth ユーザー、Edge Functions、secrets が保持されるか
  - 無料プランでの手動の一時停止の操作方法
  - 再開に失敗したときの手順
  - 再開後に、アプリ利用者が再ログインする必要があるか

## 3. 進めるかどうかの判断

```text
START
 ├─ §1 P1〜P9 と §2 R1〜R8 はすべて「済」か？ ── いいえ → 止めない（NOT GO）。何が足りないかを利用者に示す
 └─ はい
     ├─ 利用者が「anohi-memories を今から止めてよい」と明示的に承認したか？ ── いいえ → NOT GO
     └─ はい
         ├─ 一時停止を実施（利用者、または承認済みの操作）
         ├─ anohi-memories が「停止中」になったことを確認したか？ ── いいえ / 不明 → 止めた操作を取り消して再開し、§5 へ
         └─ はい
             ├─ active が 1 つ（stock-x-autopost のみ）で、新規作成の費用が 0 か？ ── いいえ / 不明 → 作成しない。§5 で写真アプリを復旧
             └─ はい
                 ├─ 利用者が「使い捨てプロジェクトを新規作成してよい」と明示的に承認したか？ ── いいえ → §5
                 └─ はい → 作成。PR122 の手順書 §2 の条件（マーカー・台帳・確認文・validate）→ §4 へ
```

**途中で必ず止める条件（ABORT）**
- プロジェクトの取り違えの疑い。
- 費用が 0 でない、または費用が不明。
- 空き枠がない。
- 再開ボタンが使えない、または再開の可否が不明。
- 担当者が不在。
- 本番（`stock-x-autopost`）に影響する可能性が見つかった。

これらに当たったら、**新しい操作をすべて止め、§5 の復旧へ**進む。有料プランへの変更や、本番の停止で解決しようとはしない。

## 4. 検証中（使い捨てプロジェクトだけを使う）

- すべての操作は、使い捨てプロジェクトの**ダミーのユーザー・ダミーのバケット・ダミーの行**だけに対して行う。家族写真のプロジェクトには、読み取りも含めて一切触れない。
- 最初は **E1（読み取りのみ）**。E2 以降は、利用者が実行ごと・実験ごとに同意したものだけを行う（PR122 の `cli.ts validate` が `REQUEST_VALID_DRY_RUN_ONLY` を返し、その出力を証跡 0 番とする）。
- 証跡は PR122 の規則に従う: 書き込み前に秘匿化、カタログ指紋の sha256、相関 ID、JST と UTC の記録。
- **UNKNOWN / FAIL が出たら、その系統の先には進まない。** PASS と書き換えない。
- E11 は R6 が「済」の場合だけ行う。実施しても、本番での D 方式の承認にはならない。
- **時間管理**（T0 = 写真アプリが停止中になったと確認できた時刻）
  - T0+60h: **新しい実験を開始しない**（残り 12 時間は撤収と復旧に使う）。
  - 有用な実験が終わった時点、または進めなくなる UNKNOWN / FAIL が出た時点で、60 時間を待たずに §5 へ進む。
  - T0+66h の時点で復旧が完了していなければ、**すぐ利用者に知らせる**。

## 5. 復旧（最優先）

1. 新しい実験を止める。進行中の手順は安全な区切りで止め、UNKNOWN として記録する。
2. 秘匿化済みの証跡（リポジトリ外）が保存されたことを確認する。
3. **空き枠を空ける**
   - 証跡が確定していれば、使い捨てプロジェクトを削除する（名前・作成日・マーカーで、使い捨てであることを確認してから。利用者の操作）。
   - 証跡がまだ確定していなければ、使い捨てプロジェクトを**一時停止**して枠を空け、削除は家族写真アプリの復旧の後に回す（一時停止中は数に入らない、とされている。その時点で再確認する）。
4. `anohi-memories` を **Resume project** で再開する（利用者、または承認済みの操作）。
5. 状態が正常（ACTIVE / healthy）になったことを確認する（Dashboard、または承認済みの接続での読み取り）。
6. **実機での確認**（利用者）: ログイン → 写真一覧 → 表示 → 1枚アップロード → 再表示。**写真の枚数が §1 P3 の基準値以上**で、写真が消えていないこと。
7. 正常でなければ、すぐに「復旧に失敗 / 保留」として記録し、家族写真アプリの回復を最優先にする。
   - 選択肢: 待つ、Supabase サポートに連絡、バックアップから戻す。
   - **有料プランへの変更は、利用者が明示的に決めた場合だけ。** 期限切れの再開オプションが有料化で戻るとしても、自動では選ばない。
8. 使用済みの ref を台帳に追加する。テスト用のダミーアカウントや OAuth アプリの後片付けを確認する。
9. 報告: 停止時刻・再開時刻（JST）、停止していた時間、実機確認の結果、実験の結果一覧（`verdict()`）。

**空き枠を空けられない、削除や一時停止が終わらない、再開できない場合**
- すぐに止めて、利用者に障害の内容を見せる。
- 「空き枠があるはず」とは仮定しない。有料化や本番の停止で回避しない。
- 次の手（待つ / サポート / バックアップ）は、利用者が決める。
