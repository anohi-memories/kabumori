## F2：切断の RPC と、確かめた人の JWT が結び付いていなかった（アプリ）
- **原因**: `use-x-connect.ts` の `disconnect()` は、A を確かめた後に `supabase.rpc()` をそのまま呼んでいた。supabase-js 2.115.0 の `fetchWithAuth` は、送るときに session を読み直し、`Authorization` が無いときだけそれを付ける。そのため、間に B がログインすると B の JWT で送られた。
- **修正**:
  - 始めた人と session（user_id と session_id）を固定する。
  - その session の token を、**この1つの request にだけ** `.setHeader('Authorization', …)` で付ける。共有の client と global header は変えていない。
  - 応答の後も、同じ人と session であるときだけ、成功やエラーを表示し、再読込する。違えば `session_changed`。
- **試験**（`apps/social-mobile/tests/x-connect-disconnect-sdk-race.test.mjs`）: 本物の `@supabase/supabase-js` を使い、Auth だけを偽物にした。8件。
  - 修正前（#523 の hook。`X_CONNECT_HOOK_SOURCE` で切り替え）は **7件 FAIL**:
    - H1 の場面では B の token が送られた
    - ログアウト中は匿名の key が送られた
    - A→B→A の新しい session の token が送られた
    - 応答を待つ間に B に替わっても「切断しました」と出た
  - 修正後は **8/8 PASS**:
    - どの場面でも、確かめた A の token だけが送られる
    - B には成功もエラーも見せない
    - 同じ session の token の更新は通る
    - 後でふつうに呼べば、SDK が今の session を使う（共有の client を変えていない）
- **サーバー側**: ログアウトの後に A の token が送られても、001 の S2-2（生きている session）が拒否する。
