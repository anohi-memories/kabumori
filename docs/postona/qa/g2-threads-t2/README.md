## 2. 結果

| ID | 組み合わせ | 判定 |
|---|---|---|
| T2-OK | その人のアカウントが Threads だけ → 解除 → 読み直しで一覧が本当に空 → 「解除しました」 | PASS（正しい成功。**修正後も残すべき**） |
| T2-F | 解除の答えのあと、再読込が**失敗**（読めない・ログイン無し）→ 一覧が空 → 「解除しました」と出て、そのまま再読込もしない | **FINDING（新しい条件、P3）** |
| T2-S | 読み直しで、まだそのアカウントが一覧にある | PASS（成功と言わない）。観察: 以後読み直さないので「確認しています…」のまま |
| T2-M | Threads を2つ接続 → A を解除 → 同じカードに B の解除ボタンが出て、その上に「解除しました」（どのアカウントか書いていない） | **FINDING（P3）** |
| T2-P | 「確認中」の間に別の人がログイン → その人の一覧には無いので、**その人に**「解除しました」と出る | **FINDING（P3）** |
| T2-L | 偽物の規則をソースの文面と照合（古い読み込みを捨てる、準備完了以外は一覧が空、カードにデータの状態を渡していない、成功の判定は一覧だけ） | PASS |

TASK の他の組み合わせ:
- 古い一覧が遅れて反映される → データ層が古い読み込みを捨てる（T2-L で照合）
- 解除の拒否・二度押し・確認後の人の入れ替わり・投稿中との競合（`PUBLISH_IN_FLIGHT` で認証情報を残す）→ G4 既存の試験で確認済み（`threads-disconnect.test.mjs` の該当試験、今回も通過）

### 負例コントロール（素朴な修正案で確かめる）
「一覧が空でないときだけ成功とする」という素朴な修正案を入れて動かした。
- 再読込の失敗では、もう成功と言わない（T2-F が反転する）。
- その一方で、本当に一覧が空になる正しい場合（T2-OK）では、ずっと「確認しています…」になり、成功を出せなくなる。

つまり、この確認一式は「止めすぎる修正」も見つけられる。

## 3. 修正後の受入条件（G4 への提案）
1. 成功の判定は、解除の答えの**後に始まった**読み込みが「準備完了」で終わり、その一覧にアカウントが無いときだけにする（データの状態か読み込みの世代番号をカードに渡す）。T2-F・#342 の T2 が反転し、T2-OK が通り続けること。
2. 再読込が失敗したら「確認できませんでした。画面を読み直してください」と出し、成功とは言わない。
3. 結果の文に、解除したアカウント（@ハンドル）を入れる（T2-M）。
4. ログイン中の人が変わったら、解除の結果の表示を消す（T2-P）。
5. 一覧にまだ残る場合（T2-S）は、時間をおいた読み直しか「もう一度確認する」ボタンを用意する（任意）。
