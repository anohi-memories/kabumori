## 3. G1 への提案（表示の意味の約束。文言の決定と変更は G1 所有者が行う）
- M1: 実際のサーバーで確かめていない限り、「同じ送信IDならサーバーは2回送らない」を事実として言わない（送信IDは「二重投稿を防ぐための仕組み」と目的として言うのはよい）。
- M2: 結果が分からないとき（結果を確認できません・処理中の確認し直し）は、送り直す前に X で投稿済みでないか確かめるよう促す。送り直しが安全だと思わせない。
- M3: 同じ送信IDの説明は、本当の確認し直しの時だけ出す（初めての送信では出さない。G2-X1 の修正を保つ）。
- M4: 結果不明・模擬を成功と言わない（今のまま）。押す文字「同じ内容・同じ送信IDで確認し直す」と結果の種類ごとの動きは変えない。
- これは G2 からの一度だけの申し送り。G1 の画面・G1 の試験は G2 から変更しない。

## 4. G2 側の更新計画（G1 の新しい HEAD 待ち）
- **関門**: G1 が2文（＋G1 の試験 722 行）を変えた HEAD を出し、H のレビューを経て、G2 の確認と同じパスに他の担当の変更が無いこと。それまでは古い HEAD での失敗を製品の欠陥と断定しない。
- **更新の対象**: G2 の新しい確認ファイルを1つ作り、#394/#403/#411/#414/#448 の固定文言の観点（出る・出ない・負例）を、新しい文言で確かめ直す。古いファイルと古い PR は書き換えない（古い HEAD の上の記録として残す）。

- **足す負例（計画、NOT_RUN）**: 同じ送信ID／処理中／結果を確認できません／模擬／確認済みの各場面で、(1) どの描かれた画面にも「サーバーは2回送らない」型の言い切りが無い、(2) 送り直しの前に X での確認を促す文がある、(3) 初めての送信では同じ送信IDの説明が無い、(4) 「出ない」確認は負例と対にする（空振り防止）。文字の完全一致ではなく、意味の部品（言い切りの言葉が無い・X での確認を促す）で判定する。
- **証拠の区分**: ソースと模擬だけ（今回の計測）／Simulator／実機／実際の API は分けて書き、実機・実 Auth・実 X・Threads API は NOT_VERIFIED のまま。
