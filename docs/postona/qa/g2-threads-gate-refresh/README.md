## 2. 流れ（ソース、#391 から変化なし）
カードで「投稿内容を確認する」ごとに新しい冪等キー → 「投稿する」で 1 回送る → サーバーの `begin` は、同じキーなら同じ記録、**このアカウントに終わっていない記録があれば `PUBLISH_IN_PROGRESS`**（`threads_manual_publish_one_open_per_account` の一意の索引でも守る）、終わった後の新しいキーは新しい記録（**本文が同じかは見ない**）→ 入れ物の作成 → 公開 → 読み直し。共有の中心部分は、同じ入れ物を二度公開せず（後戻りの遷移が無い）、結果不明は読み取りだけで確かめる（G4 の `threads_manual_publish_test.ts` が確認済み: 二度押し・同時の要求・答えの消失・結果不明の後の確認・手順の途中の期限切れ・許可の取り消し・放置された手順など）。

## 4. 準備部分について分かったこと（G2 所有）
1. G2 #391・#393 の準備部分は、useCallback が描くたびに新しい関数を返していた。手動投稿の処理部品は「依存が変わったら状態を読み直す」作りなので、その準備では**描くたびに読み直す**（実機より多く読み直し、古い画面を作れない）。今回の試験では本物どおり使い回す形にした（G2-TH で確認）。
2. #391 の準備部分は、冪等キーの番号を画面ごとに 1 から数えていた。画面が 1 つなら問題ないが、2 つにすると同じキーになる。今回は全画面で通しの番号にした。
3. #391 の 9 件を、使い回す形に直した準備で流し直すと **9 件すべて同じ結果**（T1-U・T1-PU・T1-A・T1-P の FINDING も、T1-F・T1-W・T1-R の通過も、負例も同じ）。記録: `g2-391-with-memoized-usecallback.log`。**#391 の結論は変わらない**（元の試験は無変更、一時の写しで流して削除）。
4. #393（解除）の処理部品は「依存が変わったら動く処理」を使っていないため、1 の癖の影響を受けない（ソースで確認、流し直しはしていない）。
