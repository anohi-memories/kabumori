## 1. 結論（先に）
1. **10/30 の変更そのものでは、この4つの表は壊れない**（既にある表は権限を保つ。G5 §1 [O]）。ただし本番にこの4つがあり、その権限が今のままであることは **[U]**。
2. **db reset・プレビューでは、もともと再構築できない**（10/30 とは関係なく前からある欠け）。さらに、**main の migration の並びは `20260918120000` で止まる**:
   - 空の DB では、その前提の確認が `PHASE4_PREFLIGHT_MISSING_TABLE:brands` で失敗する [P]。
   - 4つの表はどの migration でも作られていない [M]。
3. **4つのほかにも、migration の外にあるものを見つけた**（G5 の走査では出ないもの）:
   - 表 `public.brand_settings`・`public.daily_content_plans`（作る migration が無い。`20261006160200:42` が存在を前提にし、Edge が読む）[M][K]。
   - **`brand_id` の列**: `scheduled_posts`・`post_execution_logs`・`posting_windows`・`publish_claims` の4つの表は migration で作られている。しかし `brand_id` の列を足す migration が無いのに、`20260918120000` の前提と policy、X の自動投稿の migration がこの列を使う [M]。
4. **再構築の migration を後で作るときに 10/30 の後で困ること**（今の読み手に必要な最小の付与。下の §3）:
   - `authenticated` は `brands` と `social_accounts` の特定の列を読む（アプリと、本人の JWT で読む Edge）。
   - `service_role` は `brands`・`social_accounts`・`published_content_fingerprints` を読む（Edge の brand 投稿・AI Lab）。
   - これを付けずに作り直すと、42501 で読み取りが止まる（漏れではなく止まる側）。
5. **G4 の候補で新しく作る表**（custody・延長のリース・手動の公開の許可・試み・nonce）は、どれも RLS を有効にし、4つの役割から `revoke all` していて、表への付与が無い。関数の実行権は1つずつ明示している [C]。**10/30 の影響なし**（ソースの上で）。

- どれも、1つの migration に「create if not exists ＋ RLS ＋ policy ＋ `revoke all ... from public, anon, authenticated, service_role` ＋ 最小の付与」をまとめる（R-2・R-3）。
