## F4/F5 contract — adopt design B
- F4 provides `ServiceLifecycleProvider` with monotonically increasing user-scoped `epoch` and `bump(userId)`, plus `ServiceLifecycleSurface` OUTSIDE the subtree destroyed/remounted by `ServiceEnrollmentGate`. Provider is above gate and surface. Signal contains **user ID only** and no entitlement verdict, bearer token, verification proof or preview payload.
- F4 account-end result calls `bump(pinned.userId)` after an authoritative successful/already-ended server response; not on preview, user cancellation or an unconfirmed result. Surface survives same-user session rotation; on logout/cross-user switch closes, and any prior verification/consent/preview/session-scoped result is invalidated. The new session must repeat required recent-auth and preview; backend 600-second rule stays authoritative.
- F5 gate consumes **current-user epoch** only. On epoch change it invalidates cached `ready`, fails closed immediately, fetches entitlement server-side bound to the CURRENT session/current UID, and shows app content only after successful authoritative eligibility. A prior in-flight result for a different epoch/user/session MUST NOT restore `ready`. If fetch fails, stays closed with retry; no automatic start/re-enroll from refresh. Preserve existing explicit `start_x_autopost_service` semantics: ended user requires deliberate user action to re-enroll.
- Same-user `session_id` rotation invalidates stale entitlement results and uses current session for a new fetch while F4 maintains the surface. Different UID or sign-out discards all cached decisions/results. No client-only entitlement enable/disable, no cross-user leakage or stale async race.
- Where route tests need changes, coordinate F4-owned layout/route tests; F5 changes only gate-owned tests. Do not duplicate F4 provider or modify `apps/social-mobile/app/_layout.tsx` or `account-deletion.tsx`.
