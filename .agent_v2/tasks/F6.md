## 目的
PR284で決めた「アプリに依らない共通AI呼出し口の契約」を、**既存の共有部品が本当に満たすか**をオフラインで確かめ、満たさない所を差分表にする。PR284のテストは偽のOpenAI応答と記録用の偽台帳・偽CallStoreだけで通っている。今回は同じ参照Gateway（PR284、変更しない）を、本物の共有部品へ差し替えて動かす。

1. **OpenAI と Claude の両方**：本物の `openai_adapter` / `anthropic_adapter`（`executeAiRequest` 経由、fetch は偽物・`--deny-net`）で、成功・429/529/503・その他5xx・timeout・切断・JSONでない出力・schema違反・拒否の各場合に、Gatewayの答えのコード・送信回数・台帳の精算の基準（実額/上限額/0）・再送しないことが、providerによらず同じになるかを表にする。違えば差分として記録する（共有コードは直さない）。
2. **本物の台帳の guard**：`SupabaseLedgerBudgetGuard` を偽のPostgREST（fetchの偽物、ネット無し）につなぎ、Gatewayの「送る直前の再確認」（`markSent` の包み）と本物の reserve → mark_sent → settle / release の順番が契約どおりか（取り消し時は送信0・予約を返す・`no_request`、台帳の応答が読めない・拒否のときは送信0）を確かめる。
3. **本物の CallStore**：PR249の `ai_calls` migration を**隔離したローカルPostgreSQL**（socketのみ・`listen_addresses=''`、既存runnerの作法）に入れ、Gatewayの claim / complete / 重複 / 中身違い / 処理中 / 記録の喪失を、PR284の偽の保存場所と同じ答えになるか確かめる。Gatewayが保存する6種類の失敗コードと、保存の場所が受け付ける7種類のコードの対応を表にする。
4. **差分表**（docs）：契約の各項目について「今どこで守られているか（共有provider / 台帳SQL / `ai_calls` SQL / H5 bridge / 参照Gatewayだけ）」「足りない所」「直すならどのowner・どのファイル・レビューの要否」を書く。直すのは提案だけ。
