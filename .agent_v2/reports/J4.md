## P2 — public preview observations do not reach the active end's sticky identity fence

Locations: `apps/social-mobile/src/lib/postona-service-end-client.ts:20–22,40` and `:54–74`.

readPreview only reports a session to its optional seen callback. end's internal read-back passes see, but the public preview() calls readPreview() without it. The end's switched/lastSeen state is local to that invocation. Consequently, B/logout observed by a concurrent public preview is ignored by the in-flight end. The later stale A result of settle's earlier-started read overwrites its local lastSeen and can return the success plus A's warnings.

Deterministic independent reproduction using the exact PR217 factory and actual F5 PR193 lifecycle handlers over F5's synthetic world:
1. A previews and withdraws POSTONA normally. Actual F5 leaves login/account/Kabumori intact and returns Threads local_removed_remote_unverified and X uncertain count 2.
2. Let A's own final read-back finish; pause the seventh session lookup, the final settle read, before it resolves.
3. Change the harness's current session to B, or null, and await another preview() **on the same client instance**. Its session lookup positively returns B/null. B's synthetic token is rejected by the F5 Auth fake; no real API is involved. The positive session observation is still made.
4. Complete the earlier seventh lookup with its captured stale A value. end() returns ok=true with A's completion, Threads warning and count 2. This contradicts the required sticky suppression after a positive B/null observation.
5. Alternative: reject that seventh lookup after the concurrent B/null preview. end() is no longer successful, but RESULT_UNCONFIRMED still contains A's two warnings.

Negative safety assertions: **4/4 fail** (B/null × stale-A/throwing final read). Same-person concurrent-preview controls: **2/2 pass** (normal completion with A; unknown final read retains A warnings without completion). No extra withdrawal is sent.

This is not a new external caller hypothesis: AuthProvider retains the client instance via its config-bound memo, and the existing account-deletion screen's effect can call previewPostonaEnd when user/session changes (`src/app/account-deletion.tsx:47–50`) while its earlier end promise is pending. The screen's independent display binding remains effective.
