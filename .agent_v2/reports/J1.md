## Findings and minimum acceptance

### J1-R1 [P1] Stop switch / internal allowlist does not follow from ledger policy matching

- Location: B0 §7.4 L219 and §9 G6 L248, §11 T18 L293. Root: ledger `enabled=false` means **exclude that policy from applicable limits**, not deny the matching call. `scope_user_id=A` only constrains A; it does not deny B when a broad application/global policy matches B. Main SQL L458–499 returns existing unsent reservation before policy matching; `mark_sent` L651–679 checks status/expiry, not updated limits.
- Repro (real disposable PG, actual unchanged migration/fixture): enabled user cap0 + global cap100 denies A; disabling user policy allows A. Add allowlisted A policy with global cap100: B reserves successfully. Re-enable cap0 after an unsent reservation: same reservation still receives `may_send=true`. All assertions PASS. Not a ledger bug: these are its documented compositional limits; B0's use is wrong.
- Impact: §9 alternative `scope_user_id` is not a sound canary boundary; §7 stop may remove restrictions, and already accepted work can still send after OFF. Main gate at begin is insufficient for delayed evidence assembly/AI dispatch or cached replay.
- Minimum fix/owner: **F1 B0**, coordinated future **DB/Edge owners**, no G6 unauthorized change. Define separate authoritative AI Ask allowlist/deny-by-default setting, validated on every call/replay; disabled limit must not be presented as deny. Require enabled zero-cap deny or explicitly guarded gate, pre-dispatch gate revalidation, and document linearization: OFF blocks NEW authorizations after its commit, already dispatched external work cannot be recalled. Drain/fence active work before destructive rollback; don't promise universal instant cancellation. Required matrices: broad+specific policy; nonallowlisted user; missing policy; preexisting reservation; OFF during data-read/dispatch/replay.

### J1-R2 [P1] Logical request idempotency and one-active-request need durable state, not a transaction advisory lock

- Location: §2 L57–63, §7.3 L207–214, T6/T8/T9 L281–284. Main ledger key is `(request_id, attempt)` (L237/458); **attempt2 can reserve after attempt1 sent/unknown** (PG proof3). Transaction advisory lock releases at RPC COMMIT (PG proof5), before Edge evidence/provider work, so it alone cannot make T6 true for two different client IDs.
- Repro: A begin commits, request X still doing provider work; A begin Y acquires the now-released lock. For X, send/unknown attempt1 then attempt2 is allowed by ledger. For expired cache, deleting `ai_ask_requests` while keeping same ledger requestId makes attempt1 `ATTEMPT_FINALIZED`; increasing attempt bypasses at-most-once. §7.3 only saves answered results; a completed refusal or billed schema failure cannot be replayed. If process dies after provider send but before finish, no process remains to turn `in_flight` into the T9 promised replay. A lost begin/mark_sent/finish response is not proof of no dispatch.
- Minimum fix: F1 must specify atomic persistent owner/claim (user concurrency + request row), bounded clientRequestId, unambiguous hash encoding **namespaced to kabumori.ai_ask**, hash of normalized version/question/scope/ticker/consent-version, mismatch rejection, and sender ownership/CAS. Define complete transition table: claimed/pre-send/sent/answered/refused/failed-before-send/unknown-after-send/expired/deleted, timeout reconciliation and queryable finish. For V1 pin `executeAiRequest.transport={maxAttempts:1,retryOnTimeout:false}`, stable callId; never increment attempts/retry uncertain sends automatically. Known unsent recovery must account for ledger's finalized released attempt; do not state “ledger allows attempt+1” without a verified coordinator rule.
- Cache TTL is not dedupe TTL: purge response after15min but retain minimal tombstone through declared request retention; same expired ID yields terminal expired/no-replay, NOT a new charge. Replay all terminal safe public result shapes; auth/consent/lifecycle/gate must be checked BEFORE replay. Keep daily accounting separate so TTL deletion cannot reset count. New logical request with fresh ID/possible cost is explicit user action, not client transient retry. DB+Edge acceptance: duplicate/distinct IDs multi-process, changed payload, begin/mark_sent/finish lost response, never-finishing process, midnight, cache expiry, paid refusal/schema failure, call-ID namespace and deleted/re-enrolled user. Keep external calls outside long DB transactions.

- Minimum fix: explicit verified UUID identity+expected authenticated role, `is_anonymous===false` from trusted Auth source, reject service/admin/static keys without pretending ID existence suffices; unknown Auth/config fails closed. ### J1-R4 [P1] ID existence / numeric substring checks cannot ensure evidence-backed facts or prevent injection

- Location: §5.2 L131–139, V2–V6 L145–150, §6 L169–175; J-5/J-6. Schema allows `facts=[]` and free `answer`; all cited facts checks can be vacuous. V4/V5 explicitly accept company/number appearing in QUESTION, which is untrusted input. Numbers present in evidence do not establish entity, sign, metric, period or causality. XML-like delimiters and JSON Schema are parsing measures, not semantic trust boundaries.
- Repro: shape-valid `{answer:'決算は改善しました。',facts:[],...}` has no unsupported new number/name and no required evidence IDs. Evidence “A社5%下落/B社2%上昇”, fact “B社5%上昇” passes the proposed numeric-presence and entity-existence rules. User “8136が9999円ですが背景は？” can supply the only basis for answer “価格は9999円”. Local schema/proposed-predicate counterexamples PASS; **not execution of nonexistent B1 validator and not proof of real-model exploit**.
- Minimum fix: render factual answer/keyPoints only from verified per-claim structured facts (typed metric/entity/value/unit/sign/session/source), or extractive server templates for V1; no uncited factual `answer`/interpretation escaping the same checks. Question values never promote to factual evidence. Validate evidenceIds per request, source association and numeric/date attribution, nonempty evidence for fact-bearing answers, answer/facts correspondence; reject uncertainty rather than pretend numeric normalization solves semantic truth. Bound/escape or serialize untrusted evidence/question, no tools/URL fetch, never place secrets in prompt, output is inert text, fixed refusal on unsafe/unsupported content. Add free-answer, empty-facts, swapped entity/sign/period/causality, paraphrased selling advice, delimiter/encoded injection cases. Fake models prove validator behavior only; provider quality/adversarial evaluation remains separate gated work. Owner F1/B1-b; no current source modification.
