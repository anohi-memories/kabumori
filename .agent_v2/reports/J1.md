## Findings

### R1 [P2] Authorized bridge can take private exports via dynamic import without failing the import boundary

- **File/lines:** PR205 `supabase/functions/_shared/ai_provider/isolation_test.ts:199`–221 (`modImports` scans static import/export-from only); :158–167 (`relativeImports` resolves literal relative paths only); :29–41 (`walk` ignores directory symlinks). H5 `ai_consumer_bridge/isolation_test.ts:5`–18 scans only static `from` specifiers for the bridge. Ownership: **F6 guard**, with H5 only if its own guard needs coordinated strengthening. No H5 task takeover.
- **Concrete reproduction (synthetic strings only, not a source edit/network call):** append to the existing authorized bridge:

```ts
export const auditOnlyMutation = async () =>
  (await import("../ai_provider/mod.ts")).executeAiRequest;
```

  Original named imports remain unchanged; directReferences sees only the already-allowed mod.ts specifier; reachability/entrypoint arrays also unchanged because bridge already reaches provider. `modImports` never sees dynamic namespace use, so **all four provider checks and H5's native-effect/static-from check still accept** it, although unpoliced executeAiRequest/secret/ledger exports are precisely what AUTHORIZED_MOD_IMPORTS is intended to exclude. The same namespace contains other public exports; no credential lookup/provider request was made by this reproduction.
- **Additional scoped observations:** provider reachability alone also misses an Edge importing the bridge via import-map alias or constant-computed dynamic path. Those literal bridge mentions can still be caught by H5's separate substring guard, so they are NOT claimed full-suite bypasses. Actual inert scratch-directory symlink resolves in Deno but the original walker omits its alias directory and sees no reachable entrypoint. A normal literal provider import-map target IS caught by directReferences; the initial scratch hypothesis that this alias would evade it failed and was corrected to a positive control, not retained as a finding.
- **Impact:** no current unauthorized import/send found. This is a regression/security-gate hole, not runtime sandbox or Postgres privilege escalation. Future use can widen the permitted library capabilities without the promised guard catching it; the new PR205 mutation-resistant least-privilege acceptance is incomplete.
- **Minimum fix/acceptance:** parse static and dynamic imports/re-exports at the module graph/AST level and resolve the actual scoped Deno config/import maps/canonical realpaths, or explicitly fail closed on dynamic/computed/alias imports and symlinks in this constrained boundary. Inspect symbols for authorized importers; a dynamic namespace must not expose all mod.ts exports. Fail closed on unresolved edges/read errors instead of treating them as unreachable. Add the exact authorized-file dynamic case, computed path, config alias, transitive export, symlink and ordinary-static/alias negative controls. Existing static named aliases/export-star cases must continue to fail. A blanket new file/directory/namespace allowlist or swallowing the counterexample is not an acceptable fix. Focused F6 patch + delta re-review; do not restart unrelated OAuth/AI Ask reviews.

### R2 [P2] Server timeout504 may re-send a possibly billed call despite retryOnTimeout=false

- **File/lines:** PR187 `supabase/functions/_shared/ai_provider/model_policy.ts:42` and :223 promise timeouts never retry/set `retryOnTimeout:false`; PR198 bridge.ts:362–386 invokes the policy. Underlying **unchanged** errors.ts:103–105 maps HTTP504/timeout_error to retryable SERVER_ERROR with maybeBilled=true; retry.ts:46 blocks TIMEOUT only. This becomes relevant to newly exposed M1/M2 roles allowing2–3 attempts; existing market-report primary pins1 attempt and is not changed by this finding. Ownership **F6 retry-policy/contract**, H5 consumer settings must agree; no source fix in this review.
- **Repro using real candidate policy/bridge with injected fake fetch/ledger:** classifier policy maxTransportAttempts2 (existing example), first response504 `{error:{type:'timeout_error'}}`, second valid synthetic response. Bridge returns success after **2 requests under one operation/callId**, first ledger settlement outcome `unknown`, aggregate costBasis `includes_upper_bound`. All checks were left intact. Real provider billing is NOT_RUN; this shows possibility of paying for two generated attempts, not that an invoice actually charged twice.
- **Impact / limits:** both reservations are accounted and precomputed total cap applies; **no cap bypass, forgotten cost, model/provider fallback or second client replay** was observed. But clients/owners cannot rely on the unqualified “timeouts never retry / uncertain operation is not automatically resent” contract for server-reported timeouts (and connection-loss retries require the same explicit policy decision). Different `(callId,attempt)` entries do not provide at-most-once dispatch for a logical call.
- **Minimum fix/acceptance:** make server-timeout/possibly-billed retry semantics explicit and safe before use. At minimum, use maxTransportAttempts1 for consumers promising no uncertain resend. To allow transient retries, distinguish known-unsent/known-denied failures from unknown/possibly billed failures; refuse ambiguous retries by default or introduce a reviewed explicit opt-in with approved per-operation total spending contract. Correct the API/docs/tests together, don't claim retryOnTimeout:false blocks504 as-is. Test504/timeout_error, connection lost after dispatch, client timeout, known429/529, mark_sent response loss, replay and settled-unknown; maxAttempts1 must remain one request, approved retries count every attempt, no fallback. Existing Opus primary_both and legacy OpenAI behavior must remain unchanged.
