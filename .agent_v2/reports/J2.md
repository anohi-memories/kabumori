## Findings — no product fixes made

### J2-R1 [P1] F8 late positive read can restore a newer OFF decision; TTL does not bound stop latency

- Location: [PR212 pause_gate.ts L87–95](https://github.com/anohi-memories/kabumori/blob/b80d5235e4d5d3600b654d95567bb22ac5d7c962/supabase/functions/important-news-monitor/pause_gate.ts#L87), `runningUntil = now() + ttl` after awaited setting read; isolate-wide closure installed by `installNewsPauseGuard`.
- Two distinct facts: (a) the documented 1s positive cache allows a NEW AI/X/DB write after OFF within that second; this is not cancellation of an already transmitted HTTP request. (b) there is no generation/version fence on concurrent reads. A starts reading true and stalls; OFF commits; B reads false, clears cache and is refused; A's older true response returns 5s later, sets a fresh +1s positive cache, and sends X; another new call uses that cache. Thus even after a newer refusal the guard can become running again without a new authoritative true read.
- Reproduced with the actual exported `createPauseGuardedFetch`, fake clock and deferred responses: two sends after the newer false observation; clock5001 after read-start1, two total setting reads. Separate control after TTL rejects; initial false/unreadable rejects. No external HTTP was performed.
- Impact: all outward classes protected by this closure (AI, X create/token, external feed, DB claim/write/enqueue) may cross the proposed stop boundary. Existing tests explicitly advance the clock beyond TTL but do not cover out-of-order reads; their passing result is not a strict hard-stop proof. A slow setting fetch has no request deadline here.
- Minimum owner fix: F8 must define the stop linearization/quiescence contract; do not describe flip+1s as a guaranteed bound. Do not cache positive authorization across final side effects; re-read/fence final egress. Serialize/coalesce authoritative reads or invalidate stale positive results with an observation generation/epoch, bound read lifetime and measure TTL from a defensible instant. Merely ttl=0 still leaves old-read/actual-send TOCTOU, so document/check in-flight drain and reject stale reads after a newer stop. No claim of universal instantaneous recall.
- Acceptance: two overlapping reads resolved in both orders; OFF/unreadable newer than pending true; X and DB-write boundaries; multiple requests in one warm isolate; flip before response vs after authorization; bounded timeout; resume only after a fresh true. Preserve unknown/missing/malformed fail-closed and no body override. Do not use ledger/Secrets/common Dispatcher as replacement stop switches.
