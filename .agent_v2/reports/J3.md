## Findings (all reproduced, not speculative)

### R1 — P2 / F3: purge-before-finalize retry silently loses an unresolved X-post warning

Paths: `supabase/functions/social-mobile-account-delete/delete_logic.ts:193-205,263-290`; `supabase/candidates/postona_x_publish_entitlement/002_x_service_end_saga_stop.sql:112-119`.

`unconfirmedPosts` exists only in one request's memory. The pre-purge stop reads uncertain reservations, then removes their audit rows; the actual purge cascades the reservation rows. If purge commits but finalize fails/crashes, the next request resumes `state=purged`; both stop calls return `not_applicable`, so the counter restarts at zero. No durable reconstruction is possible from the removed rows.

Independent real SQL + real TS reproduction (fake user/token verification and fake X revoke only): one expired claimed reservation → fenced uncertain → actual purge COMMIT → injected finalize transport failure gives `500 FINALIZE_FAILED`; DB has `state=purged` and zero reservations. Retry uses real finalize, returns `200 {ok:true,login_deleted:false}` with no `x_posts_unconfirmed`; `xServiceEndOutcomeOf` reports `done / unconfirmedPosts=0`. X revoke was not repeated. Thus the never-confirmed post is hidden exactly on the crash/retry path, despite normal S5/E2E passing.

Impact: lost reconciliation evidence and an apparently clean completion after an unknown publish result. Minimal owner fix **F3**: checkpoint the count/reconciliation fact durably before destructive purge and return it on purged/retry paths, or refuse to discard the footprint until reconciliation is settled. Merely retaining a local variable or taking max across the two calls is insufficient. Coordinate any shared saga-storage change with **F5**; do not edit F5's migration silently. Add real purge-committed/finalize-failed and crash-after-purge retry tests, including lease takeover and no duplicate remote revoke.

### R3 — P2 / F3 + inherited F5 boundary: lease expiring during workspace-lock wait still authorizes stop mutations

Path: `supabase/candidates/postona_x_publish_entitlement/002_x_service_end_saga_stop.sql:65-69`; inherited hold `supabase/migrations/20260928160000_social_mobile_account_deletion_candidate.sql:293-300`.

The new stop relies entirely on `social_mobile_account_deletion_hold`. That function checks `lease_expires_at <= now()` **after** waiting on locks, but `now()` is transaction start, not wall clock ([PostgreSQL 17 documentation](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)). A valid-at-entry lease may already be expired when the workspace lock is obtained. There is no fresh wall-clock rejection in the new stop before mutation.

Independent two-connection PG17 proof: valid lease with one second remaining; holder locks the workspace; stop begins and `pg_stat_activity` confirms it waits on the advisory lock; holder waits 1.3 seconds. Before release, `lease_expires_at<clock_timestamp()` is true. After lock release, actual stop returns `stopped`, revokes authority and cancels planned reservations. A fresh transaction with the exact same expired lease correctly gets `SOCIAL_MOBILE_DELETION_LEASE_LOST`. This is a stale-time fence gap, not cross-user privilege escalation; the now-based hold is inherited, but the new stop's promised expiry contract demonstrably fails.

Minimal immediate owner fix **F3**: enforce the live lease using `clock_timestamp()` after awaited lock acquisition in its owned stop path before side effects, preserving deletion→workspace→row lock order and fixed lease-lost response. Coordinate a general hold/other-step hardening with **F5** separately; do not rewrite historical migration from J3. Add expired-during-wait negative test and valid-lease/concurrent-owner controls. F4/F5's other wall-clock checks do not repair this different X saga lease.
